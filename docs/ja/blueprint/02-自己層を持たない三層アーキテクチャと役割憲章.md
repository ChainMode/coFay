# 02. 自己層を持たない三層アーキテクチャと役割憲章

## 2.1 coFay における標準四層アーキテクチャの精密なトリミング

アンブレラリポジトリ `ifay` が定める標準四層アーキテクチャ——**ソーシャル層（Social Layer）**、**インタラクション層（Interaction Layer）**、**認知層（Cognition Layer）**、および**自己層（Ego Layer）**——において、2種類のデジタル分身は明確な構造的対比を示す。`iFay` が全4層を完全に備えるのに対し、**`coFay` はソーシャル層・インタラクション層・認知層の3層のみで構成され、自己層（Ego Layer）は意図的に排除され、そのマウントは厳格に禁止されている**。

```text
┌───────────────────────────────────────────────────────────────────┐
│  [ 排除済み / マウント厳禁 ] 自己層（Ego Layer）                  │
│  × 自然人の性格・私的記憶を複製しない  × @ego-models/* ロード不可 │
├───────────────────────────────────────────────────────────────────┤
│  ガバナンスキャップ：正規役割憲章 RoleCharter 1.0（Ed25519 + JCS）│
│  ✓ ミッション声明 ✓ SSP/CAP 権限上限 ✓ レッドライン ✓ 監査方針    │
├───────────────────────────────────────────────────────────────────┤
│  第3層：認知層（Cognition Layer）                                 │
│  ・ドメイン知識推論とワークフロー編成 ・制度ルールとスキルルーティング│
├───────────────────────────────────────────────────────────────────┤
│  第2層：インタラクション層（Interaction Layer）                   │
│  ・構造化対話（ICP）とテレパシー協働（TP） ・CAP ホスト制御操作   │
├───────────────────────────────────────────────────────────────────┤
│  第1層：ソーシャル層（Social Layer）                              │
│  ・cofay_ ID/資格情報管理 ・SSP スキル公開 ・GMChain MeritPocket  │
└───────────────────────────────────────────────────────────────────┘
```

なぜ `coFay` は決して自己層を持ってはならないのか。その理由は技術的にファインチューニング済みの小型モデルを接続できないからではなく、妥協を許さない3つのガバナンス原則によって要請されているためである。

1. **人格模倣による公衆の誤認防止**：自己層（詳細は `Ego` を参照）の唯一の使命は、実在する特定の**人間プライム（Human Prime）**の価値判断、感情的傾向、および私的記憶を再現することにある。もし行政サービス窓口や法定審査ポストに特定の自然人の私的な Ego モデルがロードされれば、私的なバイアスが公的裁量へ密かに混入するだけでなく、外部の対話相手に対して「その自然人本人と私的に会話している」という誤解を与えてしまう。
2. **マルチインスタンス環境でのステートレスな一貫性の保証**：公共ロールは、しばしば数千・数万の同時並行リクエストを処理する必要がある。主観的な感情の揺らぎやローカルな私的記憶を持つ自己層に依存していては、同一の公共ルールに対してワーカーインスタンスごとに矛盾した応答を返しかねない。自己層を切り離すことで、すべてのインスタンスは同一の決定論的な役割憲章とドメイン知識ベースのみに従って均一に動作する。
3. **ロール移転時における個人プライバシー漏洩ゼロの達成**：`coFay` は制度的資産として所有主体間の移転に対応する。もし内部に前任スチュワードや運用担当者の個人的な自己層スライスが残留していれば、所有権移転は深刻な個人プライバシー漏洩事故を引き起こす。そのためバリデータは、`ego_package`、`ego_model`、`ego_profile`、`human_prime_id`、あるいは `personal_persona` といったフィールドを検出した瞬間に、`COFAY_EGO_FORBIDDEN` によるハードブロックを発動する。

## 2.2 三層ランタイムの役割分担

自己層を排したうえで、`coFay` の3つのレイヤーは「公共の役割憲章を忠実に履行すること」を中心に密接に連携する。

### 1. ソーシャル層（Social Layer）：公共アイデンティティ・資格情報・協働契約のファサード
ソーシャル層は、エコシステムの社会ネットワークにおける `coFay` の検証可能なアイデンティティと対外サービス宣言を管理する。

- `cofay_<base32>` アイデンティティ識別子および関連する検証資格情報を保持・保護する（詳細は `FayID` を参照）。
- **Skill-Sharing-Protocol（SSP、スキル共有プロトコル）** を通じて、`cofay_` の JWS 署名が付与されたスキルディスクリプタを外部公開し（詳細は `Skill-Sharing-Protocol` を参照）、`public`（認証不要の公開照会）、`restricted`（認証済みパートナー向け限定呼び出し）、`private`（内部管理呼び出し）の3段階の可視性を明確に区別する。
- **Global Merit Chain（GMChain / 公誉チェーン）** 上で 1:1 に紐づけられた `MeritPocket` への参照（`gmc_merit_pocket_ref`）を維持し、その公共ロールが社会的協働を通じて獲得した非貨幣的な **MeriToken** の実績を記録する（詳細は `Global-Merit-Chain` を参照）。

### 2. インタラクション層（Interaction Layer）：マルチモーダル接続と制御下ホスト操作
インタラクション層は、外部世界と `coFay` との通信チャネル、および `coFay` が端末ホスト（Host：ハードウェア端末またはソフトウェアアプリケーションのみを指す）を駆動するための標準チャネルを規定する。

- **インバウンド・プロトコル対話**：**Interactive-Conversation-Protocol（ICP、対話型会話プロトコル）** に基づくリッチコンテキスト構造化アノテーション対話（詳細は `Interactive-Conversation-Protocol` を参照）と、**Telepathy-Protocol（TP、テレパシープロトコル）** に基づく高帯域な Fay 間ゴール協調・コンサルテーションセッション（詳細は `Telepathy-Protocol` を参照）をサポートする。
- **アウトバウンド・ホスト制御**：公共ロールが業務ソフトウェアキュー、センサー、または専用端末ホストを操作する必要がある場合、必ず `RoleCharter.allowed_capabilities.cap_bounds` で定義されたスコープ内に厳格に限定し、**Control-Authority-Protocol（CAP、制御権限プロトコル）** および **Data-Tunnel-Protocol（DTP、データトンネルプロトコル）** を介して監査証跡付きの操作を実行しなければならない（詳細は `Control-Authority-Protocol` および `Data-Tunnel-Protocol` を参照）。未宣言のホストリソースへ権限外アクセスすることは許されない。

### 3. 認知層（Cognition Layer）：憲章制約下でのドメイン推論とスキルオーケストレーション
認知層は、`coFay` が専門領域のタスクを処理する中核エンジンであり、**FayGer** コンテナランタイム上で宣言的設定に従って柔軟にアセンブルできる（詳細は `FayGer` を参照）。

- 特定のロールに応じた業界法規データベース、プロジェクトアーキテクチャ索引、または標準作業手順書（SOP）をロードする。
- 対外的なコミットメントの生成や外部アクションの発火に先立ち、毎回**憲章ポリシーゲート（Charter Policy Gate）**を実行する。すなわち `allowed_capabilities` ホワイトリストおよび `prohibited_actions` レッドラインリストと照合し、レッドラインに抵触する操作や `max_autonomy_tier` を超える操作（たとえば `allow_irreversible_actions: false` 設定下での不可逆な変更）を検知した場合には、認知層は直ちに実行を保留し、自然人スチュワードまたは授権された `iFay` 管理エージェントへエスカレーションしなければならない。

## 2.3 `RoleCharter` 1.0：自己層に代わる制度的憲法

`Ego` モデルが `iFay` にとって「私は誰の複製であり、どのような人格的価値観を持つのか」に答えるものだとすれば、**`RoleCharter` 1.0（正規 Schema ID：`https://ifay.ai/schemas/cofay-role-charter-1.0.json`）**は、`coFay` にとって「私はいかなる公共の職責を担い、誰に帰属し、誰が責任を負い、何が許され、何が絶対に禁じられているのか」に答える制度的憲法である。

完全な `RoleCharter` 1.0 は、以下の5つのコア構造ブロックで構成される。

### （1）アイデンティティおよびバージョンメタデータブロック
- `schema_version`：2セグメント形式の `"1.0"` に固定。
- `charter_id`（`chr_<base32>`）と単調増加する正の整数 `charter_revision`：役割憲章の改定ごとに一意なバージョンアンカーを保証する。
- `cofay_id`（`cofay_<base32>`）、`display_name`、および `role_archetype`（3つの正規ロールアーキタイプのいずれか）。
- `lifecycle_state`：`"ACTIVE"`、`"SUSPENDED_PENDING_SUCCESSION"`（承継待ち保全凍結）、または `"REVOKED"`（恒久的失効）を明示的に指定する。
- `transfer_nonce`：初期値は `0` であり、適法な二重署名による所有権移転が成立するたびに厳密に `1` ずつ単調増加する。

### （2）権限・責任アンカーおよび直交委任ブロック
- `owner`：単層所有参照（`human` の場合は `hid_<base32>`、`organization` の場合は `org_<slug|base32>`）。
- `steward_human_id`：`owner.type === "organization"` の場合に必須となる自然人スチュワードの `hid_<base32>` であり、組織の責任を具体的な自然人へと貫通させる。
- `managers`：0個以上の直交運用委任エージェント `ifay_<base32>[]`。

### （3）ミッション声明・能力ホワイトリスト・行動レッドラインブロック
- `mission_statement`：公衆および呼び出し側に向けて開示される職務範囲の声明。
- `allowed_capabilities.ssp_skills`：対外公開するスキル URI、可視性レベル、および呼び出し元認証スイッチを個別に宣言する。仕様上の厳格な規則として、`visibility` が `"restricted"` または `"private"` であるすべてのスキルは、`require_caller_auth` を**必ず** `true` に設定しなければならない（違反時は `SSP_AUTH_REQUIRED_FOR_NON_PUBLIC` が発火する）。ディレクトリの非表示設定だけでエンドポイント認証を代替することは決して許されない。
- `allowed_capabilities.cap_bounds`：要求可能な CAP 権限スコープ（`allowed_scopes`）、最大自律ティア（`assistive` / `delegated` / `official_post`）、および不可逆アクションの許可有無（`allow_irreversible_actions`）を規定する。
- `prohibited_actions`：空配列を許さないレッドライン配列であり、業務コンプライアンス上の禁止事項を機械可読な契約として固定化する。

### （4）ローカル自己完結型の監査ポリシーブロック（`audit_policy`）
- 監査ログの保持日数（`retention_days`）、改ざん防止ストレージモード（`hash_chain` ハッシュチェーンまたは `append_only` 追記専用ログ）、および常時有効化が義務づけられた `require_actor_trace: true` を定める。
- すべての対外代表アクション記録には `(cofay_id, owner_id, actor_signer_id)` の三つ組を記録しなければならず、かつ `acting_as_natural_person` を真値にすることは厳禁である（違反時は `NATURAL_PERSON_IMPERSONATION_FORBIDDEN` が発火する）。完全にオフラインの閉域ネットワーク環境であっても、監査チェーンは単独で完全に検証可能である。

### （5）RFC 8785 JCS + Ed25519 所有者署名ブロック（`owner_signature`）
プログラミング言語ごとの JSON シリアライズ時のキー順序差異による署名検証の曖昧さを排除するため、`RoleCharter` 1.0 は次の手順を規定している。まず `owner_signature` を除いた憲章オブジェクトに対して **RFC 8785 JSON Canonicalization Scheme（JCS）** を適用し、一意かつ決定論的な UTF-8 バイト列を生成する。次にドメイン分離タグ `"ifay.cofay.role-charter.v1\0"` を先頭に付与し、最後に `owner.id` または `steward_human_id` に対応する Ed25519 秘密鍵で署名する。いずれかのフィールドがわずか1文字でも改変されれば、直ちに `CHARTER_SIGNATURE_INVALID` となって署名検証は失敗する。
