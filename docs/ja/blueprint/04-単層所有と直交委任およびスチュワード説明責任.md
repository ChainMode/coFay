# 04. 単層所有と直交委任およびスチュワード説明責任

## 4.1 なぜ「所有権」「組織階層」「日常管理権」を完全に直交分離しなければならないのか

大規模な分散型エージェント・エコシステムにおいて最も危険なアーキテクチャ上のアンチパターンの一つは、「誰がこのエージェントを所有しているか」「親組織と子組織の上下関係がどう入れ子になっているか」「今日誰がこのエージェントを運用する権限を与えられているか」を単一のツリー構造に押し込めてしまうことである。もしある `coFay` が別の `coFay` を所有することを許したり、`iFay` が `coFay` の法的所有者になることを認めたりすれば、たちまち底なしの多段シェル構造（入れ子構造）が生まれてしまう。その結果、最終的な法的・社会的説明責任がどの自然人または法人に帰属するのかを特定できなくなるだけでなく、エージェントの権限変更時に連鎖的な障害（カスケード崩壊）を引き起こすことになる。

この問題を根本から防ぐため、`coFay` は **FayID** および **Global Merit Chain（GMChain / 公誉チェーン）** とリポジトリ横断で統一された**3つの直交軸モデル**を採用している（詳細は `FayID` および `Global-Merit-Chain` を参照）。

1. **所有軸（Ownership Axis）**：「この `coFay` の資産権と最終責任は誰に帰属するか」に答える軸であり、厳格に**単層所有（Single-Layer Ownership）**のみに制限される。
2. **組織階層軸（Organization Hierarchy Axis）**：「グループ親会社と子会社の関係はどうなっているか」に答える軸であり、`OrganizationID` 自身が持つ単一親・根付き非巡回ツリー（DAG/Tree）の内部だけで表現し、決して `coFay` の入れ子によって模倣しない。
3. **日常運用委任軸（Operational Delegation Axis）**：「どの個人デジタル分身が日常運用においてこの `coFay` を代表して当直業務にあたる権限を持つか」に答える軸であり、直交する `managers: iFayID[]` によって1ホップで付与され、所有主体そのものを変更することは一切ない。

## 4.2 単層所有の鉄則と自然人スチュワード（Steward）への貫通的説明責任

`RoleCharter` 1.0 において、すべての `coFay` はいかなる時点でもただ1つの所有主体 `owner` のみを持つ。

- **個人による直接所有**：`owner = { "type": "human", "id": "hid_<base32>" }`
- **組織による直接所有**：`owner = { "type": "organization", "id": "org_<slug|base32>" }`

`ifay_<base32>` または `cofay_<base32>` を `owner.id` に設定しようとする試みは、JSON Schema 層とランタイム検証層の双方で `OWNER_TYPE_FORBIDDEN` によって即座に拒否される。また、所有組織 `org_sub` に `FayID` 上で親組織 `org_parent` が存在する場合であっても、その `coFay` の `owner` には直接保有する `org_sub` のみが正確に記録され、親組織へ暗黙的にロールアップ（自動帰属）されることはない。

### 組織所有下における自然人スチュワード必須制約
組織は法的・協働的な抽象エンティティであり、物理的なハードウェアセキュリティ鍵を自ら直接保持したり、自然人としての倫理的審査義務を単独で遂行したりすることはできない。そのため、`RoleCharter` 1.0 は次の規則を義務づけている。

> **`owner.type === "organization"` であるすべての `coFay` は、有効な自然人スチュワード `steward_human_id`（形式は厳密に `hid_<base32>`）を明示的に宣言しなければならない。**

- `steward_human_id` が欠落している場合は、直ちに `ORG_STEWARD_REQUIRED` が発火する。
- `ifay_` や `cofay_` をスチュワードに指定しようとした場合は、直ちに `STEWARD_MUST_BE_HUMAN` が発火する。

この設計により、どれほど大規模で複雑な組織構造であっても、エコシステム内で稼働するすべてのアクティブな `coFay` には、常に役割憲章のコンプライアンスに対して直接の監督責任を負う特定可能な自然人スチュワードが存在することが保証される。

## 4.3 直交1ホップ `iFay` 管理委任と「再委任の禁止」

実運用においては、所有する自然人や組織の自然人スチュワードが、24時間すべての日常運用操作や設定ディスパッチに対して毎回自ら署名し続けることは現実的ではない。そこで所有者またはスチュワードは、信頼できる**人間プライム（Human Prime）**の監督下にある1つ以上の `iFay` を `RoleCharter.managers`（例：`["ifay_opsmanageralpha2345", "ifay_opsmanagerbravo2345"]`）に登録することができる。

この直交管理委任は、以下の3つのセキュリティ境界を厳格に遵守する。

1. **管理権は決して所有権を侵食しない**：`managers` に対する `iFay` の追加・削除は日常運用の代行範囲を調整するだけであり、`owner` は一切変化しない。管理エージェントには所有権移転を発起する権限も、`RoleCharter` のミッション声明やレッドラインを書き換える権限もない。
2. **委任対象は `iFay` のみに限定される**：日常の管理アクションは具体的な人間プライムの監督下にある個人デジタル分身を通じて行われる必要があり、別の `coFay` を当該 `coFay` の管理エージェントに指定することは厳禁である（`MANAGER_TARGET_INVALID` が発火する）。これにより、公共ロール間にまたがる循環制御ループの発生を未然に防止する。
3. **厳密な1ホップ制限・二次的な再委任の禁止（No Re-delegation）**：管理委任の `GRANT`（付与）および `REVOKE`（取消）を実行できるのは、`owner.id` または `steward_human_id` のみである。すでに権限を付与された `ifay_A` が独断で `ifay_B` へ管理権を二次委任しようとした場合、バリデータは直ちにこれを拒否して `MANAGER_REDELEGATION_FORBIDDEN` を返す。この1ホップ規律によって、権限チェーンが無秩序に拡散するリスクを完全に排除している。

## 4.4 5大基盤プロトコルを横断するエンドツーエンドの権限・責任チェーン

コンプライアンスを満たして稼働する `coFay` は、上記の権限・責任モデルをどのようにプロトコルスタック全体へ貫徹させるのか。アイデンティティの確立からスキル提供、そして評判記録に至るまでの5リポジトリ連携トポロジを以下に示す。

```text
[FayID 1.0] hid_ / org_ / ifay_ / cofay_ の自己主権型鍵と単層所有関係を確立
     │
     ▼
[coFay RoleCharter 1.0] スチュワードが憲章を発行：ロール種別、SSP/CAP 境界、managers[] を確定
     │
     ├──▶ [Faying 1.1] (coFay Delegated Stewardship Profile)
     │      Human Prime / Steward ──▶ iFay Manager ──▶ coFay の検証可能な委任認可チェーンを接続
     │
     ├──▶ [SSP 1.0 & CAP 1.0]
     │      cofay_ JWS 署名付きスキルディスクリプタを公開し、cap_bounds 内で端末ホスト(Host)を制御
     │
     └──▶ [GMChain]
            職務遂行が創出した社会的貢献を 1:1 紐づけの MeritPocket（非貨幣的 MeriToken）へ記録
```

具体的には、各プロトコルと以下のように接続される。

- **`Faying 1.1` との接続**：`Faying 1.0` は人間プライムとその個人 `iFay` の 1:1 ペアリングに特化しており、すでに仕様凍結・公開済みである。エコシステムでは後方互換性を保つ拡張である **`Faying 1.1`（`coFay` Delegated Stewardship Profile）**（詳細は `Faying-Protocol` を参照）を通じて、1.0 を一切破壊することなく「人間プライム／組織スチュワード → `iFay` 管理エージェント → `coFay`」の検証可能な委任資格情報チェーンと二重署名移転の認可セマンティクスを伝送する。
- **`SSP 1.0` との接続**：呼び出し側（通常は人間プライムの Mandate 制約下で動作する `iFay`）が `coFay` のスキルを呼び出す際、`InvocationRequest.caller.id` には正規の `FayID` が格納され、`coFay` はディスクリプタ取得時および呼び出し実行時の双方において `restricted` / `private` スキルに対する双方向認証を強制する（詳細は `Skill-Sharing-Protocol` を参照）。
- **`CAP 1.0` との接続**：`coFay` がキオスク端末や業務アプリケーションなどのホスト（Host：端末デバイスまたはソフトウェアアプリケーションのみを指す）にインハビットして制御を行う際、ホスト側ドライバは `RoleCharter.allowed_capabilities.cap_bounds` に基づいて認可ディスクリプタを検証し、`allowed_scopes` を逸脱する命令や `allow_irreversible_actions` に違反する命令を確実に遮断する（詳細は `Control-Authority-Protocol` を参照）。

## 4.5 代表行動の監査証跡とオフライン追跡可能性

いかなる紛争解決やセキュリティ振り返りにおいても事実関係を完全に復元できるよう、`coFay` は**代表関係の追跡可能性（Actor Traceability）**を、外部ネットワークや特定のブロックチェーンのオンライン状態に依存しない本質的なセマンティクス要件として定義している。

1. **自然人個人の名義では決して行動しない**：`coFay` のあらゆる対外声明および応答は、「所有主体傘下の公共ロール」の名義で行われる。監査レコード内に `acting_as_natural_person: true` が現れた場合、直ちに規約違反（`NATURAL_PERSON_IMPERSONATION_FORBIDDEN`）と判定される。
2. **必須の三つ組監査アンカー**：すべての対外呼び出し、承認、または状態変更レコードには、以下の3要素を完全に含めなければならない。
   - `cofay_id`：現在職務を遂行している公共ロールの識別子。
   - `owner_id`：アクション発生時点における法的な単層所有主体の識別子。
   - `actor_signer_id`：当該アクションに実際に署名した鍵主体（`cofay_` ロール鍵自体、所有者、スチュワード、または役割憲章内でアクティブな `ifay_` 管理エージェントのいずれか。未認可の署名者は直ちに `AUDIT_ACTOR_UNAUTHORIZED` を引き起こす）。
3. **不在時のグレースフルデグラデーション保証**：デプロイ環境がまだ `GMChain` メインネットに接続していない場合や、閉域・低速ネットワークで隔離されている場合でも、ローカルの `hash_chain` または `append_only` 監査ログが上記の三つ組署名証跡を完全に保全し、ネットワーク復旧後に必要に応じてバッチダイジェストをオンチェーンへアンカーできる。
