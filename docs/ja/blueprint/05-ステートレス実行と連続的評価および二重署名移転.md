# 05. ステートレス実行と連続的評価および二重署名移転

## 5.1 核心的ジレンマの解消：「ステートレスで置換可能なインスタンス」がいかに「連続的な貢献口座」を持つのか

公共ロール分身をシステムとして設計する際、エンジニアリングの実務では一見すると相反する2つの要件に直面する。

- **高可用性サービスの観点**：ネットワーク全体に向けてスキル協働を提供する `coFay` は、ステートレスな水平オートスケーリング、データセンター間のフェイルオーバー、およびコンテナのホットアップグレードに対応しなければならない。個々のランタイムプロセスが停止したり置き換えられたりしても、外部からの呼び出しに影響を与えてはならない。
- **社会的信用の蓄積の観点**：**Global Merit Chain（GMChain / 公誉チェーン）** は各 `cofay_<base32>` に対して独立した単一の `MeritPocket`（評判ポケット、詳細は `Global-Merit-Chain` を参照）を 1:1 で紐づけ、そのロールが高品質な公共サービスを提供して獲得した**MeriToken（最小単位は `μ` / Merit Unit）**とコミュニティガバナンス重みを長期にわたり蓄積する。

いつでも破棄・再生成できるステートレスなプロセスが、いかにして数年にわたる連続的な評価口座を保持できるのか。

`coFay` は、**「実行の弾力性はランタイム層へ沈め、アイデンティティと評判はアイデンティティ層へアンカーする」**という階層分離アーキテクチャによって、この緊張関係を完全に解消している。

```text
                       ┌────────────────────────────────────────────┐
アイデンティティ・台帳層 │ 一意の永続 ID: cofay_orgservicedesk234567  │
（状態連続・改ざん不可） │ 1:1 台帳紐づけ: GMChain MeritPocket (mpk_) │
                       │ ガバナンス契約: RoleCharter 1.0 (JCS 署名) │
                       └─────────────────────┬──────────────────────┘
                                             │ 同一の有効な役割憲章を均一ロード
                     ┌───────────────────────┼───────────────────────┐
                     ▼                       ▼                       ▼
ランタイム実行層 [FayGer Worker #1]     [FayGer Worker #2]     [FayGer Worker #N]
（ステートレス） 自己層なし・即時拡縮   自己層なし・無停止置換  遠隔地DR・オンデマンド起動
```

1. **ランタイム層の完全なステートレス性（Stateless Runtime Elasticity）**：認知推論とプロトコル解釈を担う **FayGer** ワーカーインスタンスは、ローカルに固有の人格記憶を一切保持せず（自己層 Ego なし）、起動時に検証済みの現行有効版 `RoleCharter` 1.0 と読み取り専用のドメイン知識パッケージのみをロードする。トラフィック急増時には数秒で数百インスタンスへスケールアウトし、閑散時にはゼロまでスケールインできる。
2. **暗号学的な代表署名の一元化**：複数のステートレスなワーカーインスタンスが無秩序に匿名レスポンスを返すのではなく、ハードウェアセキュリティモジュール（HSM）や閾値署名によって管理された `cofay_` 鍵保持者キー（詳細は `FayID` を参照）、または役割憲章で明示的に授権された `managers: iFayID[]` による代表署名を通じて、外部の呼び出し側および `GMChain` に対して検証可能なレシートを発行する。
3. **コンテナではなくロールへの評判集約**：外部の社会メンバーが評価・承認するのは `cofay_` という公共ロールの職務遂行品質であり、創出された非貨幣的 MeriToken の貢献記録はすべて `cofay_` に 1:1 で紐づく `MeritPocket` へと帰属する。基盤コンテナが何百回ローリングアップデートされようとも、ロールの社会的信用は途切れることなく連続する。

## 5.2 なぜ所有権移転には「二重署名アトミックプロトコル」が不可欠なのか

唯一の**人間プライム（Human Prime）**に生涯紐づく `iFay` とは異なり、制度化されたロール資産である `coFay` には正当な所有権移転のニーズが本質的に存在する。たとえば、個人開発者が立ち上げたオープンソース協働 `coFay`（`project_collaborator`）が成熟した後にオープンソース財団の組織名義へ正式移管されるケースや、組織再編に伴ってある公共サービス窓口が旧事業部門法人から新運営機関へと引き継がれるケースなどである。

しかし、所有権移転の仕組みが杜撰であれば、直ちに3つの重大なセキュリティ脆弱性が噴出する。

1. **一方的な乗っ取り・悪意ある責任押し付けの脆弱性**：片方の署名しか要求しない設計では、攻撃者が他者のロールを奪取できるか、あるいはコンプライアンス紛争やペナルティリスクを抱えた `coFay` を事情を知らない第三者の自然人や組織へ一方的に押し付けて責任を転嫁できてしまう。
2. **前任管理エージェント残留の脆弱性（Stale Manager Retention）**：移転前、旧所有者は通常、内部運用用の `managers: iFayID[]` を複数設定している。もし移転時に既存の `managers` リストをデフォルトで引き継ぎ、新所有者による事後の手動削除に委ねてしまうと、引き継ぎ直後に危険なタイムウィンドウが生じ、旧所有者側の `iFay` がすでに所有者の変わった `coFay` の名義で対外指令へ署名し続けることが可能になってしまう。
3. **過去の移転エンベロープによるリプレイ攻撃（Replay Attack）**：厳密に単調増加するリプレイ防止番号と直前の役割憲章ダイジェストの束縛がなければ、過去の移転メッセージを再送して所有権を不正にロールバックされる恐れがある。

## 5.3 `TransferEnvelope` 1.0：二重署名アトミック所有権移転の正規フロー

上記の3大リスクを根絶するため、`coFay` は標準化されたアトミック移転エンベロープ **`TransferEnvelope` 1.0**（`schemas/cofay-role-charter-1.0.json` の `$defs.TransferEnvelope` に定義）を規定している。

### ステップ1：事前状態のロックとリプレイ防止ナンスの確定
移転エンベロープを構築する際、以下の項目を明示的に記録しなければならない。

- `prior_charter_digest_hex`：現在有効な `RoleCharter` を RFC 8785 JCS で正規化した後の SHA-256 16進ダイジェスト（不一致の場合は直ちに拒否され、`PRIOR_CHARTER_DIGEST_MISMATCH` を返す）。
- `transfer_nonce`：厳密に `currentCharter.transfer_nonce + 1` と等しい値（古い番号の再送や番号飛ばしはいずれも `TRANSFER_NONCE_MISMATCH` を引き起こす）。
- `from_owner` と `to_owner`：双方が単層所有制約を満たす必要があり（`HumanID` または `OrganizationID` のみ、`ifay_` / `cofay_` の入れ子は厳禁、かつ自己への移転 `SELF_TRANSFER_REDUNDANT` も厳禁）、譲受側が `to_owner.type === "organization"` である場合は、譲受側の自然人スチュワード `new_steward_human_id` も同時に指定しなければならない。

### ステップ2：前任管理エージェントの強制クリアまたは明示的再承認（`manager_policy`）
`TransferEnvelope` 1.0 は**前任の `managers` を暗黙的に引き継ぐことを決して許さず**、以下の2択から明示的に宣言することを強制する。

- **`"CLEAR_ALL"`（デフォルトの推奨安全設定）**：`ratified_managers` は空配列 `[]` でなければならず、移転が発効した瞬間に既存のすべての `iFay` 管理エージェント権限がアトミックにゼロクリアされる。
- **`"RATIFY_NEW"`（ゼロダウンタイムでのスムーズな引き継ぎ）**：譲受側が承認する新任の `iFay` 管理エージェント一覧を `ratified_managers` に明示的に列挙する。移転エンベロープ全体が譲受側の署名で保護されるため、譲受側が明示的に裏書きした `iFay` のみが留任・着任でき、追認されなかった前任エージェントはすべてアトミックに除外される。

### ステップ3：譲渡側と譲受側の双方による Ed25519 共同署名
署名ブロックを除いた移転ペイロードを RFC 8785 JCS でシリアライズし、ドメイン分離プレフィックス `"ifay.cofay.ownership-transfer.v1\0"` を先頭に連結したうえで、以下の2つの有効な Ed25519 署名を**同時に**揃えなければならない。

- `from_signature`：現在の `owner.id` または現在の `steward_human_id` による署名。
- `to_signature`：新任の `to_owner.id` または新任の `new_steward_human_id` による署名。

いずれか一方の署名が欠けていれば直ちに `TRANSFER_DUAL_SIGNATURE_REQUIRED` が返され、鍵の偽造やペイロードの改ざんがあれば直ちに `TRANSFER_SIGNATURE_INVALID` が返される。

## 5.4 `MeritPocket` の減衰なし継承と能力喪失時の保全凍結

### 1. ロール継続に伴う `MeritPocket` の承継減衰ゼロ
`GMChain` の設計において、自然人の逝去後に親族や友人へ個人の評判を引き継ぐ場合には、個人間の評判売買を防ぐため、事前にオンチェーン登録された社会的親密度に応じた厳格な5段階の承継減衰（親密度 `0.1` 未満は承継禁止）が適用される。しかし、`coFay` の適法な二重署名移転においては、`MeritPocket` が紐づいているのは前任の所有者個人ではなく **`cofay_` 公共ロールそのもの**である。したがって `merit_continuity` が `{ "preserve_cofay_id": true, "preserve_merit_pocket": true }` を維持する限り、その公共ロールが過去に蓄積した MeriToken はロールとともに新たな所有主体の監督責任下へと完全に引き継がれ、自然人の遺産承継減衰は発動しない（詳細は `Global-Merit-Chain` を参照）。むろん、MeriToken 自体は時間経過に伴って自然減衰しベースラインへ収束するという非貨幣的法則（マイニング不可・投機不可・法定通貨との交換不可、never monetary）に厳格に従い続けるため、いかなる組織もロールの買収によって静的な特権を永久に溜め込むことはできず、質の高い公共サービスを継続提供することによってのみロールの評判を維持できる。

### 2. 組織解散またはスチュワード能力喪失時の保全凍結（`SUSPENDED_PENDING_SUCCESSION`）
もしある所有組織が法人として解散したり、登録された自然人スチュワードが突発的に職務遂行能力を喪失したりしたにもかかわらず、事前の二重署名移転が完了していなかった場合、その `coFay` はどうなるのか。

リポジトリ横断の一貫性ルール（`FayID` ADR `0003` に準拠）に従い、以下のように処理される。

- 当該 `coFay` が親組織へ**暗黙的にロールアップ帰属することは決してなく**、**責任者不在の暴走エージェントと化すこともなく**、また過去の公共実績記録が即座に破棄されることもない。
- その `lifecycle_state` は **`"SUSPENDED_PENDING_SUCCESSION"`（承継待ち保全凍結状態）**へと移行する。この状態では、日常管理エージェントの追加・削除は禁止され（`CHARTER_NOT_ACTIVE`）、新たな制限付き業務アクションの対外発行は一時停止される。
- 事前に設定された閾値ガバナンス復旧ポリシーに基づく手続き、または適法な `TransferEnvelope` 1.0 二重署名引き継ぎが完了した時点で初めて、状態は `"ACTIVE"` へと再有効化され、職務遂行を再開できる。
