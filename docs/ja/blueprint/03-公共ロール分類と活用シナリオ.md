# 03. 公共ロール分類と活用シナリオ

## 3.1 なぜ初期ロール分類体系の標準化が必要なのか

現実社会における「公共ロール」は、行政窓口での申請受付、企業のカスタマーサポート、コンプライアンス監査、学術研究における共同作業、オープンソースコミュニティのガバナンスなど、無数の専門領域にまたがっている。もし `RoleCharter` 1.0 がロール種別を一切区別しない設計であれば、権限と責任の重さに応じたデフォルトのセキュリティベースラインを設けることができない。逆に、何百もの縦割り業界をそのまま列挙型としてハードコードしてしまえば、コアプロトコルの汎用性と将来の拡張性が損なわれてしまう。

そこで `coFay` では、**「対外サービストポロジ・裁量権の境界・ポストのライフサイクル」**という互いに直交する3つの特性に基づき、第1期の3大正規ロールアーキタイプ（`role_archetype`）を定義している。

1. **`org_service`（組織公共サービス窓口）**
2. **`functional_post`（法定・ガバナンス職能ポスト）**
3. **`project_collaborator`（プロジェクト・専門協働ユニット）**

すべての有効な `RoleCharter` 1.0 ドキュメントは、`role_archetype` フィールドにおいて上記3つのいずれかを明示的に宣言しなければならない（範囲外の値が指定された場合は直ちに `ROLE_ARCHETYPE_INVALID` が発火する）。

## 3.2 アーキタイプ1：`org_service`（組織公共サービス窓口）

### 位置づけと中核的特徴
`org_service` は、企業、公的機関、業界団体、または独立したサービス提供者が外部に向けて開設する**標準化された相談対応・業務受付・スキル提供のフロント窓口**を表す。外部の呼び出し側が最も頻繁に接するタイプの `coFay` である。

- **典型的な所有形態**：通常は `OrganizationID`（例：`org_civic-service-bureau`）に帰属し、自然人スチュワード `steward_human_id` を紐づける。個人事業主や独立した専門事務所であれば、`HumanID` に直接帰属させることも可能である。
- **推奨される CAP 自律ティア**：一般に `assistive` または `delegated` に設定し、`allow_irreversible_actions` を `false` とする。これにより、情報照合、チケット振り分け、予約スケジューリング、および定型スキル応答は自動化しつつ、重大な権利・義務の変更を伴う処理についてはバックエンドの自然人スチュワードまたは授権された `iFay` による再審査へと引き継ぐ。
- **SSP スキル公開の特徴**：認証不要の `public` 案内照会スキルと、呼び出し元認証を必須（`require_caller_auth: true`）とする `restricted` 業務手続きスキルを組み合わせて公開するケースが多い。

### 代表的な導入シナリオ：市政許認可・公共相談窓口
ある市の行政サービス局が、市政許認可サービス窓口 `cofay_orgservicedesk234567` をデプロイしたとする。市民は煩雑な行政手続案内ページを探し回る必要はなく、自身の個人 `iFay` に向かって「新しく地域書店を開業するために必要な消防・営業届出書類を確認して」と指示するだけでよい。

1. 市民の `iFay` は **SSP** を介して該当する行政 `coFay` を発見し、まずその `RoleCharter` 1.0 に記された `org_civic-service-bureau` の所有関係および自然人スチュワードの Ed25519 署名を検証する。
2. 整合性を確認したうえで、市民の `iFay` は公開照会スキルを呼び出して必要書類リストを取得し、人間プライム本人から明示的な承認を得た後、制限付き受付スキルを通じて事前審査パッケージを提出する。
3. 行政 `coFay` のバックエンドでは朝のピーク時間帯のアクセス急増に対応するため数十個のステートレスなワーカーインスタンスを並列稼働させることができ、発行されるすべての事前審査受領証には監査可能な `(cofay_id, owner_id, actor_signer_id)` の記録が付与される。

## 3.3 アーキタイプ2：`functional_post`（法定・ガバナンス職能ポスト）

### 位置づけと中核的特徴
`functional_post` は、組織内部、機関間コンソーシアム、またはエコシステム基盤において、**明確な制度上の職権、承認責任、あるいはコンプライアンス証明義務を担う常設の職責ポスト**を表す。その中核理念は「ポストは不変であり、当直の担当者は交代する」という制度設計にある。

- **典型的な所有形態**：ガバナンス委員会、財団、企業の内部統制部門などの `OrganizationID` に帰属し、現職の自然人スチュワード `steward_human_id` の紐づけが必須となる。
- **CAP `Official_Post` セマンティクスとの接続**：**Control-Authority-Protocol（CAP、制御権限プロトコル）** においては、機微性の高い機器や重要インフラの操作に際し、公職・法定ポスト（`Official_Post`）による認可ディスクリプタの発行または連署が求められる場合がある（詳細は `Control-Authority-Protocol` を参照）。`functional_post` 型の `coFay` はまさにこのポストセマンティクスをロール層で正規に担う器であり、`cap_bounds.max_autonomy_tier` として `"official_post"` を宣言できる。
- **人事ローテーションと評判の連続性**：ある期のセキュリティ監査官の任期が満了し、新任の監査官が着任する際、組織は該当 `coFay` の `steward_human_id` および日常運用の当直リスト `managers: iFayID[]` を更新し、改定番号（`charter_revision + 1`）を進めた新しい `RoleCharter` を発行するだけでよい。ポスト自体の `cofay_` 識別子、外部からの購読参照、およびオンチェーンの `MeritPocket` に刻まれた職務実績は一切途切れることなく継承される。

### 代表的な導入シナリオ：Global Merit Chain エコシステム安全監査ポストと無人機空域ディスパッチポスト
- **エコシステム・ガバナンス安全監査ポスト**：あるオープンソース・セキュリティ連盟が、常設の脆弱性開示・パッチ検証ポスト `cofay_govpostauditor234567` を設置する。各プロジェクトはセキュリティ勧告をこのポストへ送信し、当番のセキュリティ専門家は授権された各自の `iFay` 管理エージェントを通じて再現検証と署名承認を遂行する。外部システムは常設ポストの公開鍵チェーンのみを信頼すればよい。
- **産業パーク低空物流ディスパッチポスト**：産業パークの管理委員会が空域ルート管制用の `functional_post` 型 `coFay` を設置し、配送ロボットの端末ホスト（Host）と CAP / DTP を介して連携する。気象異常を検知した際には、役割憲章のレッドライン規定に基づき飛行停止・帰投指令を自動的に発令する。

## 3.4 アーキタイプ3：`project_collaborator`（プロジェクト・専門協働ユニット）

### 位置づけと中核的特徴
`project_collaborator` は、特定のオープンソースリポジトリ、共同研究プロジェクト、標準化ワーキンググループ、または企業横断の特別エンジニアリング施策のために編成され、**ドメイン知識グラフ、自動化ツールチェーン、および協働ワークフローを集約する公共のチームメイト・エンドポイント**として機能する。

- **典型的な所有形態**：立ち上げ初期にはプロジェクト発起人の `HumanID` が直接作成・保有できる。その後プロジェクトが成熟し、オープンソース財団への寄贈や正式な研究機関への移管が行われる際には、二重署名によるアトミックな所有権移転（`TransferEnvelope` 1.0）によって財団の `OrganizationID` へとシームレスに引き継ぐことができる。外部の呼び出し側が設定済みの `cofay_` アドレスを変更する必要は一切ない。
- **マルチプロトコル協働の強み**：**Interactive-Conversation-Protocol（ICP、対話型会話プロトコル）** を活用して設計文書・論文・コード規約に対する構造化された `.ctx` アノテーションを生成し、さらに **Telepathy-Protocol（TP、テレパシープロトコル）** を介して複数のコントリビューターの個人 `iFay` と制限付き共有ワークスペースを構築する用途に極めて適している（詳細は `Interactive-Conversation-Protocol` および `Telepathy-Protocol` を参照）。

### 代表的な導入シナリオ：機関横断の共同研究およびオープンプロトコル適合性協働ユニット
ある多言語オープンプロトコル・ワーキンググループが、`cofay_ossprojectbot234567`（アーキタイプは `project_collaborator`）を立ち上げたとしよう。世界中の異なるタイムゾーンにいるコントリビューターは、メンテナがオンラインになるのを待つことなく、各自の `iFay` からこの協働ユニットへ直接接続できる。プロトコルテストベクターの事前チェックや9言語間の用語一貫性検証が自動実行され、構造化されたレビューコメントが `.ctx` アノテーション形式でコントリビューターに返却される。この協働ユニットによる高品質なレビューがコミュニティから評価されると、非貨幣的な社会的貢献指標である **MeriToken**（マイニング不可・投機不可）がプロジェクト協働ユニットの `MeritPocket` に継続的に記録され、専門プロジェクトとしての公共的貢献が正確に可視化される。

## 3.5 3大ロールアーキタイプ能力構成クイックリファレンス

| 比較項目 | `org_service` | `functional_post` | `project_collaborator` |
|----------|---------------|-------------------|------------------------|
| **第一の設計目標** | 高並行・標準化された公衆／顧客サービスの受付 | 権限と責任が厳格な常設ガバナンス・承認・コンプライアンス証明 | 専門知識の集約、多者間研究開発協働、および移転可能な進化 |
| **一般的な所有主体** | `OrganizationID`（または個人事業者の `HumanID`） | `OrganizationID`（自然人スチュワードの紐づけ必須） | 初期は `HumanID` が多く、成熟期に `OrganizationID` へ移転 |
| **SSP スキル可視性** | `public` + `restricted` の組み合わせが中心 | 認証必須の `restricted` / `private` が中心 | `public`（オープン協働）または `restricted`（メンバー協働） |
| **CAP 最大自律ティア** | `assistive` / `delegated` | `delegated` / `official_post` | `assistive` / `delegated` |
| **典型的な交代・移転イベント** | バックエンド運用チーム `managers` のローテーション | ポストのスチュワード交代（`cofay_` ID は不変） | 個人発起人から財団・組織への二重署名移転 |
