# 04. 단일 계층 소유와 직교 위임 및 스튜어드 책임성

## 4.1 '소유권', '조직 계층', '일상 운영권'을 완전히 직교 분리해야 하는 이유

대규모 분산 에이전트 생태계에서 가장 치명적인 아키텍처 안티패턴 중 하나는 '누가 이 에이전트를 소유하는가', '조직의 상하위 부서는 어떻게 중첩되는가', 그리고 '오늘 누가 이 에이전트를 운영하도록 위임받았는가'라는 세 가지 서로 다른 관계를 하나의 트리에 뒤섞어 넣는 것입니다. 만약 어떤 `coFay`가 또 다른 `coFay`를 소유하도록 허용하거나, 개인 화신인 `iFay`가 `coFay`의 법적 소유자로 등록되도록 허용한다면 순식간에 끝을 알 수 없는 다단계 페이퍼컴퍼니식 중첩 구조가 만들어집니다. 그 결과 법적·사회적 최종 책임이 어느 자연인이나 법인에 귀속되는지 규명할 수 없게 되고, 대리인 권한을 한 번 변경할 때마다 연쇄적인 권한 붕괴가 일어납니다.

이를 원천적으로 방지하기 위해 `coFay`는 **FayID** 및 **Global Merit Chain(GMChain, 공예체인)**과 교차 저장소 수준에서 완전히 정렬된 **3대 직교 축 모델**을 집행합니다(`FayID` 및 `Global-Merit-Chain` 참조).

1. **소유 축(Ownership Axis)**: '이 `coFay`의 재산권과 최종 책임은 누구에게 속하는가'에 답하며, **단일 계층 소유**로 엄격히 제한됩니다.
2. **조직 계층 축(Organization Hierarchy Axis)**: '그룹 모회사와 자회사는 어떤 상하 관계를 맺고 있는가'에 답하며, 오직 `OrganizationID` 자체의 단일 부모 루트 비순환 트리(Single-Parent Rooted DAG/Tree) 내부에서만 표현됩니다. 결코 `coFay` 중첩 소유로 조직 구조를 흉내 내지 않습니다.
3. **일상 운영 위임 축(Operational Delegation Axis)**: '일상적인 운영 업무에서 어떤 개인 화신이 이 `coFay`를 대리해 당직을 설 수 있는가'에 답하며, 소유 주체를 전혀 건드리지 않고 직교 필드인 `managers: iFayID[]`를 통해 단일 홉으로 부여됩니다.

## 4.2 단일 계층 소유 철칙과 자연인 스튜어드(Steward) 관통 책임성

`RoleCharter` 1.0 규격에서 모든 `coFay`는 어느 시점에나 오직 단 하나의 소유 주체 `owner`만을 가집니다.

- **개인 직접 소유**: `owner = { "type": "human", "id": "hid_<base32>" }`
- **조직 직접 소유**: `owner = { "type": "organization", "id": "org_<slug|base32>" }`

`owner.id` 자리에 `ifay_<base32>`나 `cofay_<base32>`를 넣으려는 모든 시도는 JSON Schema 계층과 런타임 검증 계층 양쪽에서 즉시 `OWNER_TYPE_FORBIDDEN` 오류로 거부됩니다. 설령 소유 조직인 `org_sub`가 `FayID` 상에서 상위 모조직 `org_parent`를 두고 있더라도, 해당 `coFay`의 `owner`에는 직접 보유 주체인 `org_sub`만 정확히 기재되며 모조직으로 암묵적 자동 승격(Roll-up)되지 않습니다.

### 조직 소유 시 자연인 스튜어드 의무 지정 제약
조직은 법률 및 협업을 위한 추상적 엔티티이므로 물리적 하드웨어 보안 키를 직접 손에 쥐고 보관하거나 자연인 고유의 윤리적 재검토 의무를 스스로 수행할 수 없습니다. 따라서 `RoleCharter` 1.0은 다음의 강제 규칙을 부과합니다.

> **`owner.type === "organization"`인 모든 `coFay`는 반드시 적법한 자연인 스튜어드 `steward_human_id`(형식: `hid_<base32>`)를 명시적으로 선언해야 합니다.**

- `steward_human_id`가 누락되면 즉시 `ORG_STEWARD_REQUIRED` 오류가 발생합니다.
- `ifay_` 또는 `cofay_` 식별자를 스튜어드 자리에 지정하려 하면 즉시 `STEWARD_MUST_BE_HUMAN` 오류가 발생합니다.

이 설계 덕분에 조직 규모나 지배구조가 아무리 거대하고 복잡하더라도 생태계에서 가동 중인 모든 활성 `coFay` 뒤에는 헌장 준수 여부를 직접 감독하고 책임지는 구체적인 자연인 스튜어드가 언제나 명확히 특정됩니다.

## 4.3 직교 단일 홉 `iFay` 운영 위임과 '재위임 엄격 금지'

실제 서비스 운영 환경에서 소유 자연인이나 조직 스튜어드가 매 순간 모든 일상 배포·구성·응답 서명에 직접 개인키를 사용할 수는 없습니다. 이를 위해 소유 주체 또는 스튜어드는 신뢰할 수 있는 **인간 프라임(Human Prime)**들이 운용하는 하나 이상의 `iFay`를 `RoleCharter.managers` 배열(예: `["ifay_opsmanageralpha2345", "ifay_opsmanagerbravo2345"]`)에 등록하여 일상 운영을 위임할 수 있습니다.

직교 운영 위임은 세 가지 엄격한 보안 경계를 따릅니다.

1. **운영권은 소유권을 절대 침범하지 않음**: `managers` 목록에 특정 `iFay`를 추가하거나 제외하는 작업은 일상적인 운영 대리 범위만 조정할 뿐 `owner` 필드는 조금도 변하지 않습니다. 운영 위임 관리자는 소유권 이전을 발의할 권한이 없으며, `RoleCharter`의 사명 선언문이나 금지 레드라인을 임의로 수정할 수도 없습니다.
2. **피위임 대상은 오직 `iFay`로만 한정**: 일상 운영 행위는 구체적인 인간 프라임의 후견 아래 작동하는 개인 화신을 통해서만 수행되어야 합니다. 다른 `coFay`를 현재 `coFay`의 운영 위임 관리자로 지정하는 행위는 즉시 차단되며(`MANAGER_TARGET_INVALID`), 이로써 공공 역할 간 순환 제어 루프가 형성될 가능성을 원천 봉쇄합니다.
3. **엄격한 단일 홉과 재위임 금지(No Re-delegation)**: 오직 `owner.id` 또는 `steward_human_id`만이 운영 위임의 부여(`GRANT`) 및 철회(`REVOKE`)를 수행할 수 있습니다. 이미 권한을 위임받은 `ifay_A`가 임의로 제3의 `ifay_B`에게 운영 권한을 다시 넘기려 시도하면 검증기는 즉시 거부하고 `MANAGER_REDELEGATION_FORBIDDEN`을 반환합니다. 이 단일 홉 규율은 권한 사슬이 통제 불능 상태로 확산되는 위험을 완전히 제거합니다.

## 4.4 5대 핵심 인프라를 관통하는 엔드투엔드 권한·책임 협업 사슬

적합성을 갖춘 `coFay`는 위에서 정의한 권한·책임 모델을 전체 프로토콜 스택에 어떻게 관통시킬까요? 신원 생성부터 스킬 제공과 평판 기록에 이르는 5개 저장소 간 협업 토폴로지는 다음과 같습니다.

```text
[FayID 1.0] hid_ / org_ / ifay_ / cofay_ 자기주권 키 및 단일 계층 소유 관계 확립
     │
     ▼
[coFay RoleCharter 1.0] 스튜어드가 헌장 서명 발행: 역할 아키타입, SSP/CAP 경계, managers[] 확정
     │
     ├──▶ [Faying 1.1] (coFay Delegated Stewardship Profile)
     │      Human Prime / Steward ──▶ iFay Manager ──▶ coFay 검증 가능한 위임 권한 체인 연결
     │
     ├──▶ [SSP 1.0 & CAP 1.0]
     │      cofay_ JWS 서명 스킬 기술자 외부 발행 및 cap_bounds 범위 내 단말 호스트(Host) 통제 조작
     │
     └──▶ [GMChain]
            직무 수행으로 창출한 사회적 기여를 1:1 바인딩된 MeritPocket에 기록 (비화폐적 평판치 MeriToken)
```

구체적인 프로토콜 간 연동 방식은 다음과 같습니다.
- **`Faying 1.1`과의 연동**: `Faying 1.0`은 인간 프라임과 개인용 `iFay` 간의 1:1 페어링에 집중하며 이미 동결 배포되었습니다. 생태계는 하위 호환성을 완벽히 유지하는 **`Faying 1.1`(`coFay` Delegated Stewardship Profile)** 확장을 통해(`Faying-Protocol` 참조), 1.0 규격을 훼손하지 않고도 '인간 프라임/조직 스튜어드 → `iFay` 운영 위임 관리자 → `coFay`'로 이어지는 검증 가능한 위임 자격증명 체인과 이중 서명 소유권 이전 승인 시맨틱을 전달합니다.
- **`SSP 1.0`과의 연동**: 외부 호출자(통상 인간 프라임의 Mandate 제약을 받는 `iFay`)가 `coFay`의 스킬을 호출할 때 `InvocationRequest.caller.id`에 표준 `FayID`를 담아 전송하며, `coFay`는 기술자 조회 단계와 실제 실행 단계 양쪽에서 `restricted` / `private` 스킬에 대해 양방향 인증을 강제합니다(`Skill-Sharing-Protocol` 참조).
- **`CAP 1.0`과의 연동**: `coFay`가 무인 키오스크나 업무용 애플리케이션 호스트(Host)에 깃들어(Inhabit) 제어 명령을 내릴 때, 호스트 드라이버는 `RoleCharter.allowed_capabilities.cap_bounds`를 기준으로 권한 기술자를 대조 검증하여 `allowed_scopes`를 벗어나거나 `allow_irreversible_actions` 제약을 위반하는 명령을 즉시 차단합니다(`Control-Authority-Protocol` 참조).

## 4.5 대외 대표 행위 감사 추적과 오프라인 역추적성 보장

분쟁 조정이나 보안 사고 사후 분석 상황에서 언제든 사실관계를 완벽히 복원할 수 있도록, `coFay`는 **대표 관계의 역추적성**을 외부 네트워크 연결이나 특정 블록체인 노드의 온라인 여부에 좌우되지 않는 내재적 시맨틱 요건으로 규정합니다.

1. **자연인 개인 명의 사칭 절대 금지**: `coFay`의 모든 대외 선언과 응답은 오직 '소유 주체 산하 공공 역할'의 명의로만 이루어집니다. 감사 로그 레코드에 `acting_as_natural_person: true`가 기록되는 순간 즉시 규정 위반(`NATURAL_PERSON_IMPERSONATION_FORBIDDEN`)으로 판정됩니다.
2. **필수 3원 감사 앵커 기록**: 모든 대외 호출, 심사 승인 또는 상태 변경 로그에는 다음 세 가지 식별자가 빠짐없이 포함되어야 합니다.
   - `cofay_id`: 직무를 수행한 공공 역할 식별자
   - `owner_id`: 행위 발생 시점의 법적 단일 계층 소유 주체 식별자
   - `actor_signer_id`: 해당 액션에 실제로 암호학적 서명을 수행한 키 주체(`cofay_` 자체 역할 키, 소유 주체, 스튜어드, 또는 헌장 내 활성 `ifay_` 운영 위임 관리자 중 하나만 허용되며 미승인 서명자는 즉시 `AUDIT_ACTOR_UNAUTHORIZED` 유발)
3. **인프라 부재 시 우아한 성능 저하 보장**: 배포 환경이 아직 `GMChain` 메인넷에 연결되지 않았거나 폐쇄망·불안정 네트워크 환경에 놓여 있더라도, 로컬 `hash_chain` 또는 `append_only` 감사 로그가 위 3원 튜플 서명 증거를 온전히 보존하며 추후 네트워크가 복구되었을 때 배치 다이제스트를 온체인에 선택적으로 앵커링할 수 있습니다.
