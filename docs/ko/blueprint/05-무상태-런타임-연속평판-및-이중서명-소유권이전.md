# 05. 무상태 런타임, 연속 평판 및 이중 서명 소유권 이전

## 5.1 핵심 긴장 관계 해법: '언제든 교체 가능한 무상태 인스턴스'가 어떻게 '연속 기여 계정'을 갖는가

공공 역할 화신을 엔지니어링 관점에서 설계할 때 흔히 겉보기에 서로 모순되는 두 가지 요구사항과 마주치게 됩니다.
- **고가용성 서비스 관점**: 전체 네트워크를 대상으로 스킬 협업을 제공하는 `coFay`는 무상태(Stateless) 수평 오토스케일링, 리전 간 장애 조치(Failover), 컨테이너 무중단 핫 업그레이드를 지원해야 합니다. 개별 런타임 프로세스 하나가 종료되거나 새 컨테이너로 교체되더라도 외부 호출에는 티끌만한 영향도 없어야 합니다.
- **사회적 신뢰 축적 관점**: **Global Merit Chain(GMChain, 공예체인)**은 모든 `cofay_<base32>`마다 고유한 단일 `MeritPocket`(평판 포켓, `Global-Merit-Chain` 참조)을 1:1로 바인딩하여, 해당 역할이 양질의 공공 서비스를 제공하며 쌓아 올린 **평판치(MeriToken, 최소 단위 `μ` / Merit Unit)**와 커뮤니티 거버넌스 가중치를 수년에 걸쳐 연속으로 누적합니다.

언제든 파기하고 다시 띄울 수 있는 무상태 프로세스가 어떻게 수년간 이어지는 연속 평판 계정을 보유할 수 있을까요?

`coFay`는 **'실행 탄력성은 런타임 계층으로 내리고, 신원과 평판은 신원·원장 계층에 고정한다'**는 계층 분리 아키텍처로 이 긴장을 깔끔하게 해소합니다.

```text
                      ┌────────────────────────────────────────────┐
신원 및 원장 계층     │  유일 영구 신원: cofay_orgservicedesk234567 │
(상태 연속·위변조 불가)│  1:1 바인딩 원장: GMChain MeritPocket(mpk_) │
                      │  거버넌스 앵커: RoleCharter 1.0 (JCS 서명)  │
                      └─────────────────────┬──────────────────────┘
                                            │ 동일한 현행 유효 헌장 일괄 로드
                    ┌───────────────────────┼───────────────────────┐
                    ▼                       ▼                       ▼
런타임 실행 계층 [FayGer Worker #1]     [FayGer Worker #2]     [FayGer Worker #N]
(무상태 탄력성)   자아 계층 없음/즉시 확장 자아 계층 없음/핫 교체  다중 리전 DR/온디맨드 기동
```

1. **런타임 계층의 완전한 무상태화(Stateless Runtime Elasticity)**: 인지 추론과 프로토콜 파싱을 수행하는 **FayGer** 워커 인스턴스는 로컬 디스크나 메모리에 독점적인 사적 인격 기억을 일절 보관하지 않으며(자아 계층 Ego 배제), 부팅 시 검증을 통과한 현행 유효 `RoleCharter` 1.0과 읽기 전용 도메인 지식 번들만 로드합니다. 트래픽이 급증하면 수초 내에 수백 개 인스턴스로 수평 확장하고, 유휴 시간대에는 0개로 축소할 수 있습니다.
2. **암호학적 대표 서명의 단일 창구 통합**: 여러 무상태 워커 인스턴스가 제각기 익명 응답을 남발하는 것이 아니라, 하드웨어 보안 모듈(HSM)이나 임계치 서명(Threshold Signature)으로 보호되는 `cofay_` 보유자 키(`FayID` 참조) 또는 헌장에 명시적으로 승인된 `managers: iFayID[]` 대리 서명을 거쳐 외부 호출자와 `GMChain`에 검증 가능한 영수증을 발행합니다.
3. **컨테이너가 아닌 역할 자체에 귀속되는 평판**: 외부 사회 구성원이 품질을 평가하고 신뢰를 보내는 대상은 일시적인 컨테이너가 아니라 `cofay_`라는 공공 역할 자체입니다. 따라서 창출된 비화폐적 MeriToken 기여 기록은 모두 `cofay_`와 1:1로 묶인 `MeritPocket`으로 일원화되어 쌓이며, 하부 컨테이너 이미지가 수백 번 교체·업그레이드되더라도 역할의 사회적 공신력은 끊김 없이 유지됩니다.

## 5.2 소유권 이전이 반드시 '이중 서명 원자적 프로토콜'이어야 하는 이유

유일한 **인간 프라임(Human Prime)**에게 평생 귀속되어 양도가 금지되는 `iFay`와 달리, 제도적 역할 자산인 `coFay`는 현실 거버넌스에서 적법한 소유권 이관 수요가 자연스럽게 발생합니다. 예를 들어 개인 개발자가 시작한 오픈소스 협업 `coFay`(`project_collaborator`)가 성장한 뒤 공익 오픈소스 재단 법인 명의로 정식 이관되거나, 기업 구조 개편 과정에서 특정 대민 서비스 창구가 기존 사업부 법인에서 신설 운영 기관으로 넘어가는 경우가 대표적입니다.

그러나 소유권 이전 메커니즘을 허술하게 설계하면 곧바로 세 가지 치명적인 보안 취약점이 터져 나옵니다.
1. **일방적 탈취 또는 악의적 책임 떠넘기기 취약점**: 한쪽 당사자의 서명만으로 이전이 가능하다면 공격자가 타인의 역할을 탈취할 수 있거나, 반대로 법적 분쟁이나 평판 제재 위험을 안고 있는 문제성 `coFay`를 전혀 모르는 제3의 자연인이나 조직 앞으로 일방적으로 떠넘겨 책임을 전가할 수 있습니다.
2. **전임 운영 위임 관리자 잔류 취약점(Stale Manager Retention)**: 이전 전 소유 주체는 대개 내부 운영을 위해 여러 `managers: iFayID[]`를 등록해 둡니다. 만약 소유권 이전 시 기존 `managers` 목록을 암묵적으로 그대로 유지하고 새 소유자가 나중에 수동으로 지우도록 방치한다면, 인수인계 직후의 위험한 시간 창(Time Window) 동안 전임 조직 소속 `iFay`가 이미 소유 주체가 바뀐 `coFay` 명의로 대외 명령을 계속 서명·발행할 수 있게 됩니다.
3. **과거 이전 봉투 리플레이 취약점(Replay Attack)**: 엄격히 단조 증가하는 리플레이 방지 시퀀스 번호와 직전 헌장 다이제스트 바인딩이 없으면, 과거에 사용된 적법한 이전 패킷을 재전송해 소유권을 강제로 과거 상태로 되돌리는 공격이 가능해집니다.

## 5.3 `TransferEnvelope` 1.0: 이중 서명 원자적 소유권 이전 표준 절차

위 세 가지 보안 위협을 근원적으로 차단하기 위해 `coFay`는 표준 원자적 소유권 이전 봉투 규격인 **`TransferEnvelope` 1.0**을 정의합니다(`schemas/cofay-role-charter-1.0.json` 내부 `$defs.TransferEnvelope`에 포함).

### 제1단계: 직전 헌장 상태 고정 및 리플레이 방지 번호 검증
소유권 이전 봉투를 생성할 때는 다음 필드를 반드시 명시적으로 기록해야 합니다.
- `prior_charter_digest_hex`: 현재 유효한 `RoleCharter`를 RFC 8785 JCS로 정규화한 바이트열의 SHA-256 16진수 다이제스트입니다(불일치 시 즉시 `PRIOR_CHARTER_DIGEST_MISMATCH` 오류로 거부).
- `transfer_nonce`: 정확히 `currentCharter.transfer_nonce + 1`과 일치해야 합니다(과거 번호 재사용이나 번호 건너뛰기 시 즉시 `TRANSFER_NONCE_MISMATCH` 발생).
- `from_owner` 및 `to_owner`: 양측 모두 단일 계층 소유 제약을 충족해야 하며(`HumanID` 또는 `OrganizationID`만 허용, `ifay_` / `cofay_` 중첩 소유 차단, 자기 자신에게로의 무의미한 이전은 `SELF_TRANSFER_REDUNDANT`로 차단), 양수인 `to_owner.type === "organization"`인 경우 반드시 양수 측의 새로운 자연인 스튜어드 `new_steward_human_id`를 함께 지정해야 합니다.

### 제2단계: 전임 운영 위임 관리자 강제 초기화 또는 명시적 재인준(`manager_policy`)
`TransferEnvelope` 1.0은 **전임 `managers` 목록의 암묵적 승계를 절대 허용하지 않으며**, 다음 두 가지 정책 중 하나를 반드시 선택하도록 강제합니다.
- **`"CLEAR_ALL"` (기본 권장 보안 모드)**: `ratified_managers`를 반드시 빈 배열 `[]`로 두어야 하며, 소유권 이전이 발효되는 즉시 기존의 모든 `iFay` 운영 위임 권한이 원자적으로 초기화됩니다.
- **`"RATIFY_NEW"` (무중단 매끄러운 인수 모드)**: 양수인이 승인한 신임 `iFay` 운영 위임 관리자 목록을 `ratified_managers`에 명시적으로 기재합니다. 이전 봉투 전체가 양수인의 서명으로 덮이므로 양수인이 명시적으로 배서한 `iFay`만 자격을 유지하거나 부여받으며, 추인받지 못한 전임 대리인은 모두 원자적으로 제거됩니다.

### 제3단계: 양도인과 양수인의 양방향 Ed25519 공동 서명
서명 블록을 제외한 이전 페이로드를 RFC 8785 JCS로 직렬화하고 도메인 분리 접두사 `"ifay.cofay.ownership-transfer.v1\0"`을 결합한 뒤, 다음 **두 개의 유효한 Ed25519 서명을 동시에** 확보해야 합니다.
- `from_signature`: 현행 `owner.id` 또는 현행 `steward_human_id`가 수행한 서명
- `to_signature`: 신임 `to_owner.id` 또는 신임 `new_steward_human_id`가 수행한 서명

어느 한쪽 서명이라도 빠지면 즉시 `TRANSFER_DUAL_SIGNATURE_REQUIRED`가 반환되며, 키 위조나 페이로드 변조가 감지되면 즉시 `TRANSFER_SIGNATURE_INVALID`가 반환됩니다.

## 5.4 `MeritPocket` 무감가 연속성과 유고 시 보전 동결

### 1. 역할 연속성 하에서의 `MeritPocket` 승계 감가 제로 원칙
`GMChain`의 기본 설계에서 자연인이 사망한 뒤 유족이나 지인에게 개인 평판을 승계할 때는 개인 평판 매매를 막기 위해 온체인에 사전 등록된 사회적 관계 친밀도에 따라 엄격한 5단계 승계 감가율을 적용합니다(친밀도가 `0.1` 미만이면 승계 자체가 금지됨). 반면 `coFay`의 적법한 이중 서명 소유권 이전에서는 `MeritPocket`이 전임 소유 개인이 아니라 **`cofay_` 공공 역할 자체**에 바인딩되어 있습니다. 따라서 `merit_continuity`가 `{ "preserve_cofay_id": true, "preserve_merit_pocket": true }`를 유지하는 한, 해당 공공 역할이 그동안 쌓아 온 MeriToken은 자연인 유산 감가 없이 역할과 함께 신임 소유 주체의 책임 감독 아래 온전히 이어집니다(`Global-Merit-Chain` 참조). 물론 MeriToken 자체는 시간 경과에 따라 자연 감쇠하여 바닥값(Floor)으로 수렴하는 비화폐적(non-monetary) 법칙을 그대로 따릅니다. 즉 어떤 조직도 역할을 인수하는 것만으로 영구적인 정적 특권을 사재기할 수 없으며, 오직 양질의 공공 서비스를 꾸준히 제공해야만 역할의 높은 평판도를 유지할 수 있습니다.

### 2. 조직 말소 또는 스튜어드 유고 시 보전 동결(`SUSPENDED_PENDING_SUCCESSION`)
만약 소유 조직이 해산·말소되거나 등록된 자연인 스튜어드에게 갑작스러운 유고가 발생했는데 사전에 이중 서명 소유권 이전이 완료되지 않은 상태라면 해당 `coFay`는 어떻게 처리될까요?
교차 저장소 정합성 규칙(`FayID` ADR `0003` 정렬)에 따라 다음 절차가 작동합니다.
- 해당 `coFay`는 상위 모조직으로 **암묵적 자동 승격되지 않으며**, **책임자 없이 폭주하는 무주공산 에이전트로 방치되지도 않고**, 그동안 쌓인 공공 평판 기록이 즉시 파기되지도 않습니다.
- 대신 `lifecycle_state`가 즉시 **`"SUSPENDED_PENDING_SUCCESSION"`(승계 대기 보전 동결 상태)**으로 전환됩니다. 이 상태에서는 일상 운영 위임 관리자의 추가·삭제가 차단되고(`CHARTER_NOT_ACTIVE`), 새로운 제한 등급 대외 업무 액션 발행도 일시 정지됩니다.
- 사전에 설정된 임계치 거버넌스 복구 정책에 따른 승계 절차를 밟거나 적법한 `TransferEnvelope` 1.0 이중 서명 인수가 완료된 후에야 비로소 상태가 `"ACTIVE"`로 재활성화되어 정상 직무를 재개할 수 있습니다.
