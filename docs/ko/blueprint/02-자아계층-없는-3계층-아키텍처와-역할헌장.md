# 02. 자아 계층 없는 3계층 아키텍처와 역할 헌장

## 2.1 표준 4계층 아키텍처에서 coFay에 적용된 정밀 절삭

상위 우산 저장소 `ifay`가 확립한 표준 4계층 아키텍처—**소셜 계층(Social Layer)**, **상호작용 계층(Interaction Layer)**, **인지 계층(Cognition Layer)**, **자아 계층(Ego Layer)**—위에서 두 유형의 디지털 화신은 명확한 구조적 분기를 보입니다. `iFay`가 네 계층을 모두 온전히 갖추는 것과 달리, **`coFay`는 오직 소셜 계층·상호작용 계층·인지 계층의 3계층으로만 구성되며 자아 계층(Ego Layer)을 명시적으로 절삭하고 탑재를 엄격히 금지합니다**.

```text
┌───────────────────────────────────────────────────────────────────┐
│  [ 절삭됨 / 탑재 엄격 금지 ] 자아 계층 (Ego Layer)                │
│  × 자연인의 성격·사적 기억 복제 불가   × @ego-models/* 로드 금지  │
├───────────────────────────────────────────────────────────────────┤
│  거버넌스 상부 캡: 표준 역할 헌장 RoleCharter 1.0 (Ed25519 + JCS) │
│  ✓ 사명 선언문  ✓ SSP/CAP 권한 상한  ✓ 금지 레드라인  ✓ 감사 정책 │
├───────────────────────────────────────────────────────────────────┤
│  제3계층: 인지 계층 (Cognition Layer)                             │
│  · 도메인 지식 추론 및 워크플로 오케스트레이션                    │
│  · 제도적 규칙 판정 및 스킬 라우팅 의사결정                       │
├───────────────────────────────────────────────────────────────────┤
│  제2계층: 상호작용 계층 (Interaction Layer)                       │
│  · 구조화 대화(ICP) 및 텔레파시 협업(TP)  · CAP 호스트 통제 조작  │
├───────────────────────────────────────────────────────────────────┤
│  제1계층: 소셜 계층 (Social Layer)                                │
│  · cofay_ 신원 및 자격증명 관리 · SSP 스킬 발행 · GMChain 평판 포켓│
└───────────────────────────────────────────────────────────────────┘
```

왜 `coFay`는 결코 자아 계층을 가져서는 안 될까요? 미세 조정된 소형 언어 모델을 기술적으로 붙일 수 없어서가 아니라, 결코 타협할 수 없는 세 가지 거버넌스 원칙 때문입니다.

1. **인격 모사로 인한 대중 오인 방지**: 자아 계층(`Ego` 저장소 참조)의 유일한 존재 목적은 특정 실제 **인간 프라임(Human Prime)**의 가치 판단 기준, 감정적 결, 사적 기억을 정교하게 복제하는 데 있습니다. 만약 공공 민원 창구나 법정 인허가 심사 석(席)이 특정 자연인의 개인용 Ego 모델을 로드한다면, 사적인 편향이 공적 재량 판단에 은밀히 스며들 뿐 아니라 외부 이용자가 마치 그 자연인 당사자와 사적인 대화를 나누고 있다고 착각하게 만듭니다.
2. **다중 인스턴스 무상태 일관성 보장**: 공공 역할은 수천~수만 건의 동시 협업 요청을 병렬로 처리해야 하는 경우가 흔합니다. 주관적인 감정 흔들림이나 로컬 전용 사적 기억을 지닌 자아 계층에 의존하면 워커 인스턴스마다 동일한 공공 규칙에 대해 서로 모순된 응답을 내놓게 됩니다. 자아 계층을 제거하면 모든 워커 인스턴스가 오직 동일한 결정론적 역할 헌장과 도메인 지식 베이스에 의해 일관되게 제어됩니다.
3. **역할 소유권 이전 시 개인 프라이버시 유출 제로 보장**: `coFay`는 제도적 자산으로서 소유 주체 간 적법한 이관을 지원합니다. 만약 내부에 전임 스튜어드나 운영 담당자의 개인 자아 계층 슬라이스가 조금이라도 남아 있다면, 소유권을 넘기는 순간 심각한 개인정보 유출 사고로 이어집니다. 따라서 검증기는 `ego_package`, `ego_model`, `ego_profile`, `human_prime_id`, `personal_persona` 필드가 하나라도 감지되면 즉시 `COFAY_EGO_FORBIDDEN` 오류를 발생시켜 실행을 원천 차단합니다.

## 2.2 3계층 런타임의 직무 분담

자아 계층을 덜어낸 자리에서 `coFay`의 3계층 아키텍처는 '공공 역할 헌장의 충실한 이행'이라는 단일 목표를 중심으로 긴밀하게 맞물려 작동합니다.

### 1. 소셜 계층(Social Layer): 공공 신원, 자격증명 및 협업 계약 파사드
소셜 계층은 생태계 협업 네트워크 안에서 `coFay`의 검증 가능한 신원과 대외 서비스 선언을 관리합니다.
- `cofay_<base32>` 신원 식별자와 이에 연결된 검증 자격증명을 안전하게 보관·관리합니다(`FayID` 참조).
- **스킬 공유 프로토콜(SSP)**을 통해 `cofay_` JWS 서명이 첨부된 스킬 기술자(Descriptor)를 외부에 발행하며(`Skill-Sharing-Protocol` 참조), `public`(비로그인 공개 조회), `restricted`(인증된 파트너 제한 호출), `private`(내부 운영 전용 호출)의 3단계 가시성 등급을 명확히 구분합니다.
- **Global Merit Chain(GMChain, 공예체인)** 위에서 1:1로 바인딩된 `MeritPocket` 회계 매핑 참조(`gmc_merit_pocket_ref`)를 유지하며, 해당 공공 역할이 사회적 협업을 제공해 적립한 비화폐적 **평판치(MeriToken)**를 투명하게 기록합니다(`Global-Merit-Chain` 참조).

### 2. 상호작용 계층(Interaction Layer): 멀티모달 접속과 통제된 호스트 제어
상호작용 계층은 외부 세계가 `coFay`와 소통하는 인바운드 채널과, `coFay`가 단말 호스트(Host, 오직 단말 하드웨어 기기나 소프트웨어 애플리케이션만 지칭)를 구동하는 아웃바운드 표준 채널을 정의합니다.
- **인바운드 프로토콜 상호작용**: **상호작용 대화 프로토콜(ICP)** 기반의 풍부한 컨텍스트 구조화 주석 대화(`Interactive-Conversation-Protocol` 참조)와, **텔레파시 프로토콜(TP)** 기반의 고대역폭 교차 Fay 목표 정렬 및 자문 세션(`Telepathy-Protocol` 참조)을 지원합니다.
- **아웃바운드 호스트 제어**: 공공 역할이 업무용 소프트웨어 큐, 산업용 센서 또는 전용 키오스크 호스트를 조작해야 할 때는 반드시 `RoleCharter.allowed_capabilities.cap_bounds`에 명시된 권한 범위 안에서만 **제어 권한 프로토콜(CAP)** 및 **데이터 터널 프로토콜(DTP)**을 통해 감사 가능한 동작을 수행해야 합니다(`Control-Authority-Protocol` 및 `Data-Tunnel-Protocol` 참조). 헌장에 선언되지 않은 호스트 리소스에 접근하는 월권 행위는 원천 차단됩니다.

### 3. 인지 계층(Cognition Layer): 헌장 제약 하의 도메인 추론 및 스킬 오케스트레이션
인지 계층은 `coFay`가 전문 도메인 과업을 처리하는 핵심 추론 엔진으로, **FayGer** 컨테이너 런타임 안에서 선언적 설정에 따라 탄력적으로 조립·구동됩니다(`FayGer` 참조).
- 해당 역할에 부합하는 산업 법규집, 프로젝트 아키텍처 인덱스 또는 표준 운영 절차(SOP)를 로드합니다.
- 대외적 약속을 생성하거나 외부 액션을 트리거하기 직전마다 반드시 **헌장 사전 정책 게이트(Charter Policy Gate)** 검사를 수행합니다. `allowed_capabilities` 허용 목록과 `prohibited_actions` 레드라인 목록을 대조하여, 금지 조항에 저촉되거나 `max_autonomy_tier` 상한을 초과하는 요청(예: `allow_irreversible_actions: false` 상태에서 비가역적 상태 변경 시도)이 감지되면 인지 계층은 즉시 실행을 보류하고 자연인 스튜어드나 승인된 `iFay` 운영 위임 관리자에게 에스컬레이션합니다.

## 2.3 `RoleCharter` 1.0: 자아 계층을 대체하는 제도적 헌법

`Ego` 모델이 개인용 `iFay`에게 '나는 누구로부터 복제되었으며 어떤 인격적 결을 지니는가'를 답해 준다면, **`RoleCharter` 1.0(표준 Schema ID: `https://ifay.ai/schemas/cofay-role-charter-1.0.json`)**은 `coFay`에게 '나는 어떤 공공 직무를 맡고, 누구에게 귀속되며, 누가 최종 책임을 지고, 무엇을 할 수 있으며 무엇을 절대 해서는 안 되는가'를 규정하는 제도적 헌법입니다.

완전한 `RoleCharter` 1.0 문서는 다섯 개의 핵심 구조 블록으로 이루어집니다.

### (1) 신원 및 버전 메타데이터 블록
- `schema_version`: 두 자리 버전 문자열 `"1.0"`으로 고정됩니다.
- `charter_id`(`chr_<base32>`) 및 단조 증가 양의 정수 `charter_revision`: 헌장이 개정될 때마다 고유한 버전 앵커를 보장합니다.
- `cofay_id`(`cofay_<base32>`), `display_name`, 그리고 3대 표준 아키타입 중 하나를 지정하는 `role_archetype` 필드를 포함합니다.
- `lifecycle_state`: `"ACTIVE"`(정상 가동), `"SUSPENDED_PENDING_SUCCESSION"`(승계 대기 보전 동결), `"REVOKED"`(영구 폐기) 중 하나를 명시적으로 선언합니다.
- `transfer_nonce`: 초기값은 `0`이며, 적법한 이중 서명 소유권 이전이 성사될 때만 정확히 `1`씩 단조 증가합니다.

### (2) 권한·책임 고정 및 직교 위임 블록
- `owner`: 단일 계층 소유 주체 참조입니다(`human`일 때 `hid_<base32>`, `organization`일 때 `org_<slug|base32>`).
- `steward_human_id`: `owner.type === "organization"`일 때 의무적으로 기재해야 하는 자연인 스튜어드 `hid_<base32>`로, 조직의 법적·윤리적 책임이 구체적인 자연인까지 관통하도록 보장합니다.
- `managers`: 일상 운영을 위임받은 0개 이상의 직교 운영 대리인 배열 `ifay_<base32>[]`입니다.

### (3) 사명 선언문, 역량 허용 목록 및 금지 레드라인 블록
- `mission_statement`: 일반 대중과 외부 호출자에게 공개하는 직무 범위 선언문입니다.
- `allowed_capabilities.ssp_skills`: 외부에 노출할 스킬 URI, 가시성 등급, 호출자 인증 강제 여부를 항목별로 선언합니다. 규격상 `visibility`가 `"restricted"` 또는 `"private"`인 모든 스킬은 `require_caller_auth`가 **반드시** `true`여야 합니다(위반 시 `SSP_AUTH_REQUIRED_FOR_NON_PUBLIC` 발생). 디렉터리에서 목록만 숨기는 방식으로 엔드포인트 인증을 대체하는 보안 꼼수는 절대 허용되지 않습니다.
- `allowed_capabilities.cap_bounds`: 요청 가능한 CAP 권한 스코프(`allowed_scopes`), 최대 자율성 등급(`assistive` / `delegated` / `official_post`), 비가역적 동작 허용 여부(`allow_irreversible_actions`)를 엄격히 제한합니다.
- `prohibited_actions`: 비어 있을 수 없는 레드라인 배열로, 도메인 규정 준수 금지 조항을 기계 판독 가능한 계약으로 고정합니다.

### (4) 로컬 자족형 감사 정책 블록(`audit_policy`)
- 감사 로그 보존 일수(`retention_days`), 위변조 방지 저장 모드(`hash_chain` 해시 체인 또는 `append_only` 추가 전용 로그), 그리고 필수 활성화 항목인 `require_actor_trace: true`를 규정합니다.
- 모든 대외 대표 행위 레코드에는 반드시 `(cofay_id, owner_id, actor_signer_id)` 3원 튜플이 기록되어야 하며, `acting_as_natural_person` 플래그를 참(true)으로 설정하는 행위는 엄격히 금지됩니다(위반 시 `NATURAL_PERSON_IMPERSONATION_FORBIDDEN` 발생). 외부 망과 단절된 폐쇄망 환경에서도 감사 추적 체인은 자체적으로 완결 검증됩니다.

### (5) RFC 8785 JCS + Ed25519 소유자 서명 블록(`owner_signature`)
프로그래밍 언어별 JSON 키 정렬 순서 차이로 인해 서명 검증 결과가 달라지는 모호성을 원천 제거하기 위해, `RoleCharter` 1.0은 엄격한 정규화 서명 절차를 강제합니다. 먼저 `owner_signature` 필드를 제외한 헌장 객체를 **RFC 8785 JSON Canonicalization Scheme(JCS)**으로 변환해 유일하고 결정론적인 UTF-8 바이트열을 생성한 뒤, 앞부분에 도메인 분리 태그 `"ifay.cofay.role-charter.v1\0"`을 결합하고 `owner.id` 또는 `steward_human_id`에 대응하는 Ed25519 개인키로 서명합니다. 헌장 내 어느 필드든 단 한 글자만 변조되어도 즉시 `CHARTER_SIGNATURE_INVALID` 검증 실패가 반환됩니다.
