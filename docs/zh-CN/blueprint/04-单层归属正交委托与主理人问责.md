# 04. 单层归属、正交委托与主理人问责

## 4.1 为什么要把「归属权」「组织层级」与「日常管理权」彻底正交解耦

在大型分布式代理生态中，最危险的架构反模式之一，就是把「谁拥有这个代理」「组织上下级怎么嵌套」与「今天谁被授权操作这个代理」混压在同一棵树里。如果允许一个 `coFay` 去拥有另一个 `coFay`，或者允许一个 `iFay` 作为 `coFay` 的法律归属所有者，很快就会衍生出深不见底的多跳壳嵌套：既无法回答最终法律与社会问责落在哪个自然人或法人头上，也会在代理权限变更时引发级联雪崩。

为此，`coFay` 与 **FayID**、**公誉链（GMChain）** 跨仓统一执行**三条正交轴模型**（详见 `FayID` 与 `Global-Merit-Chain`）：

1. **归属轴（Ownership Axis）**：回答「这个 `coFay` 的产权与最终责任属于谁」——严格限制为**单层归属**；
2. **组织层级轴（Organization Hierarchy Axis）**：回答「集团母公司与子公司之间是什么关系」——完全在 `OrganizationID` 自身的单父有根无环树中表达，绝不借用 `coFay` 嵌套来模拟；
3. **日常管理委托轴（Operational Delegation Axis）**：回答「哪些个体化身被授权在日常运维中代表该 `coFay` 执勤」——通过正交的 `managers: iFayID[]` 单跳授予，绝不改变归属主体。

## 4.2 单层归属铁律与自然人主理人（Steward）穿透问责

在 `RoleCharter` 1.0 中，每个 `coFay` 在任意时刻有且仅有一个归属主体 `owner`：

- **个人直接归属**：`owner = { "type": "human", "id": "hid_<base32>" }`；
- **组织直接归属**：`owner = { "type": "organization", "id": "org_<slug|base32>" }`。

任何试图将 `ifay_<base32>` 或 `cofay_<base32>` 填入 `owner.id` 的行为，都会在 Schema 层与运行校验层同时遭到 `OWNER_TYPE_FORBIDDEN` 拒绝。即便归属组织 `org_sub` 在 `FayID` 中存在母组织 `org_parent`，该 `coFay` 的 `owner` 也只能精确填写直接持有它的 `org_sub`，不会隐式上卷为母组织。

### 组织归属下的自然人主理人强制约束
组织是法律与协作抽象实体，无法亲自保管物理硬件安全密钥或独立承担自然人伦理审查义务。因此，`RoleCharter` 1.0 规定：

> **凡 `owner.type === "organization"` 的 `coFay`，必须显式声明合法的自然人主理人 `steward_human_id`（格式严格为 `hid_<base32>`）。**

- 缺失 `steward_human_id` 将直接触发 `ORG_STEWARD_REQUIRED`；
- 试图将 `ifay_` 或 `cofay_` 充当主理人将直接触发 `STEWARD_MUST_BE_HUMAN`。

这一设计确保了无论组织架构多么庞大，生态中的每一个活跃 `coFay` 都始终有一名明确可定位的自然人主理人对其章程合规性负直接监管责任。

## 4.3 正交单跳 `iFay` 管理委托与「禁止再委托」

在实际运营中，归属自然人或组织主理人不可能每分每秒亲自签署每一次日常运维与配置调度。为此，归属方或主理人可以将一个或多个受信任人类原型的 `iFay` 列入 `RoleCharter.managers`（如 `["ifay_opsmanageralpha2345", "ifay_opsmanagerbravo2345"]`）。

正交管理委托严格遵循三条安全边界：

1. **管理权绝不染指所有权**：向 `managers` 增删任何 `iFay` 仅调整日常运营代表范围，`owner` 保持纹丝不动；管理代理无权发起所有权过户，也无权篡改 `RoleCharter` 的使命与红线。
2. **被委托主体仅限 `iFay`**：日常管理动作需要依托具体人类原型监护下的个体化身完成，严禁将另一个 `coFay` 指派为当前 `coFay` 的管理代理（触发 `MANAGER_TARGET_INVALID`），防止形成跨公共角色的循环控制环路。
3. **严格单跳，严禁二次转委托（No Re-delegation）**：只有 `owner.id` 或 `steward_human_id` 有权执行 `GRANT` / `REVOKE` 管理委托。若已获授权的 `ifay_A` 试图私自把管理权再转授给 `ifay_B`，校验器立即拒绝并返回 `MANAGER_REDELEGATION_FORBIDDEN`。这一单跳纪律彻底消除了权限链失控扩散的风险。

## 4.4 跨五大基础设施的端到端权责协同链路

一个合规运行的 `coFay` 如何将上述权责模型贯穿至整个协议栈？下面展示从身份创立到技能服务与声誉记账的完整五仓协同拓扑：

```text
[FayID 1.0] 确立 hid_ / org_ / ifay_ / cofay_ 自主主权密钥与单层归属关系
     │
     ▼
[coFay RoleCharter 1.0] 主理人签发章程：锁定角色原型、SSP/CAP 边界与 managers[]
     │
     ├──▶ [Faying 1.1] (coFay Delegated Stewardship Profile)
     │      打通 Human Prime / Steward ──▶ iFay Manager ──▶ coFay 可验证委托授权链
     │
     ├──▶ [SSP 1.0 & CAP 1.0]
     │      对外暴露带 cofay_ JWS 签名的技能描述符；在 cap_bounds 内受控操作终端宿主(Host)
     │
     └──▶ [GMChain]
            将履职创造的社会贡献记入 1:1 绑定的 MeritPocket（非货币美誉值 MeriToken）
```

具体而言：
- **与 `Faying 1.1` 的衔接**：`Faying 1.0` 聚焦于人类原型与其个人 `iFay` 的一对一配对且已发布冻结；生态通过向后兼容的 **`Faying 1.1`（`coFay` Delegated Stewardship Profile）** 扩展（详见 `Faying-Protocol`），在不破坏 1.0 的前提下承载「人类原型/组织主理人 → `iFay` 管理代理 → `coFay`」的可验证委托凭证链与双签过户授权语义。
- **与 `SSP 1.0` 的衔接**：调用方（通常为受人类原型 Mandate 约束的 `iFay`）在调用 `coFay` 技能时，`InvocationRequest.caller.id` 携带规范 `FayID`，而 `coFay` 在描述符获取与调用执行两侧对 `restricted` / `private` 技能强制执行双向鉴权（详见 `Skill-Sharing-Protocol`）。
- **与 `CAP 1.0` 的衔接**：当 `coFay` 附身（Inhabit）并控制某台自助终端或业务应用宿主（Host）时，宿主驱动依据 `RoleCharter.allowed_capabilities.cap_bounds` 核验授权描述符，拦截任何越出 `allowed_scopes` 或违反 `allow_irreversible_actions` 的指令（详见 `Control-Authority-Protocol`）。

## 4.5 代表行为审计留痕与离线可追溯性

为了确保在任何争端或安全复盘中都能还原真相，`coFay` 将**代表关系可追溯性**定义为不依赖外部网络或特定区块链在线状态的本征语义要求：

1. **绝不以自然人个人名义行事**：`coFay` 的一切对外声明与响应均以「归属主体旗下的公共角色」名义作出；审计记录一旦出现 `acting_as_natural_person: true`，立即判定违规（`NATURAL_PERSON_IMPERSONATION_FORBIDDEN`）。
2. **强制三元审计锚点**：每一次对外调用、审批或状态变更记录，都必须完整包含：
   - `cofay_id`：当前履职的公共角色标识；
   - `owner_id`：行为发生时刻的法定单层归属主体标识；
   - `actor_signer_id`：实际签署该次动作的密钥主体（可为 `cofay_` 角色密钥本身、归属方、主理人或章程内活跃的某个 `ifay_` 管理代理；非授权签名者立即触发 `AUDIT_ACTOR_UNAUTHORIZED`）。
3. **缺席可降级保证**：即使某部署环境暂未接入 `GMChain` 主网或处于弱网隔离状态，本地 `hash_chain` / `append_only` 审计日志依然完备保存上述三元组签名证据，待网络恢复后再按需锚定批次摘要。
