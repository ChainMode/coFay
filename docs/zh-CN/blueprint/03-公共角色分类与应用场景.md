# 03. 公共角色分类与应用场景

## 3.1 为什么需要规范化的首期角色分类法

在现实社会中，「公共角色」横跨政务受理、企业客服、合规审计、科研协作与开源社区治理等无数细分行业。如果 `RoleCharter` 1.0 完全不区分角色类型，或者反过来按上百个垂直行业硬编码枚举，都会带来严重的工程问题：前者无法为不同权责等级的角色设定差异化的默认安全基线；后者则会让核心协议失去通用性与演进弹性。

为此，`coFay` 按**「对外服务拓扑、裁量权边界与席位生命周期」**三个正交特征，确立了首期三大规范角色原型（`role_archetype`）：

1. **`org_service`（组织公共服务窗口）**
2. **`functional_post`（法定/治理职能席位）**
3. **`project_collaborator`（项目/专项协作单元）**

所有合法的 `RoleCharter` 1.0 文档都必须在 `role_archetype` 字段中显式声明上述三者之一（超出范围立即触发 `ROLE_ARCHETYPE_INVALID`）。

---

## 3.2 原型一：`org_service`（组织公共服务窗口）

### 定位与核心特征
`org_service` 代表企业、公共机构、行业协会或独立服务提供者对外开设的**标准化咨询、业务受理与技能服务门面**。它是外部调用方最常接触的一类 `coFay`。

- **典型归属形态**：通常归属于 `OrganizationID`（如 `org_civic-service-bureau`）并挂接自然人主理人 `steward_human_id`；个体商户或独立执业工作室亦可直接归属于 `HumanID`。
- **CAP 自主等级建议**：通常配置为 `assistive` 或 `delegated`，并将 `allow_irreversible_actions` 设为 `false`，即允许自动完成信息核验、工单分拣、预约排期与标准化技能响应，但涉及重大权益变更时转交后台主理人或授权 `iFay` 复核。
- **SSP 技能暴露特征**：往往混合暴露免鉴权的 `public` 指南查询技能与强制鉴权（`require_caller_auth: true`）的 `restricted` 业务办理技能。

### 典型落地场景：市政许可与公共咨询窗口
某市行政服务局部署了一个市政许可服务窗口 `cofay_orgservicedesk234567`。市民无需翻找繁杂的部门办事指南网页，只需向自己的个人 `iFay` 发出指令：「帮我核对新开社区书店所需的消防与经营备案材料」。
1. 市民的 `iFay` 通过 **SSP** 发现该政务 `coFay`，首先验证其 `RoleCharter` 1.0 上的 `org_civic-service-bureau` 归属与主理人 Ed25519 签名；
2. 确认无误后，市民 `iFay` 调用公开查询技能获取材料清单，并在获得人类原型明确授权后，通过受限受理技能提交预审包；
3. 政务 `coFay` 的后台可同时运行数十个无状态工作实例应对早高峰请求，所有预审回执均携带可审计的 `(cofay_id, owner_id, actor_signer_id)` 记录。

## 3.3 原型二：`functional_post`（法定/治理职能席位）

### 定位与核心特征
`functional_post` 代表组织内部、跨机构联盟或生态基础设施中**具有明确制度职权、审批职责或合规见证义务的常设岗位席位**。它的核心理念是「铁打的席位，流水的当值人」。

- **典型归属形态**：归属于治理委员会、基金会、企业内控部门等 `OrganizationID`，强制绑定当任自然人主理人 `steward_human_id`。
- **与 CAP `Official_Post` 的语义衔接**：在 **控制权限协议（CAP）** 中，部分高敏感设备或关键基础设施操作要求由公职/法定岗位（`Official_Post`）签发或会签授权描述符（详见 `Control-Authority-Protocol`）。`functional_post` 型 `coFay` 正是这一席位语义在角色层的规范承载者，其 `cap_bounds.max_autonomy_tier` 可声明为 `"official_post"`。
- **人员轮岗与声誉连续性**：当某届安全审计官任期届满、新任审计官接任时，组织只需更新该 `coFay` 的 `steward_human_id` 与日常执勤 `managers: iFayID[]` 并发布新修订号（`charter_revision + 1`）的 `RoleCharter`，而席位本身的 `cofay_` 标识、外部订阅引用以及链上 `MeritPocket` 历史履职记录保持零中断延续。

### 典型落地场景：公誉链生态安全审计席与无人设备空域签派席
- **生态治理合规审计席**：某开源安全联盟设立常设漏洞披露与补丁核验席位 `cofay_govpostauditor234567`。各项目方将安全通告推送至该席位；值班安全专家通过各自获授权的 `iFay` 管理代理驱动该席位完成复现校验与签章背书，所有外界系统只需信任该常设席位公钥链即可。
- **园区低空物流签派席**：园区管委会设立空域航线签派 `functional_post` `coFay`，与配送机器人的终端宿主通过 CAP / DTP 交互，在气象异常时依据章程红线自动下发禁飞停靠指令。

## 3.4 原型三：`project_collaborator`（项目/专项协作单元）

### 定位与核心特征
`project_collaborator` 面向特定开源仓库、科研联合课题、标准工作组或跨企业专项工程组建，作为**聚合领域知识图谱、自动化工具链与协作工作流的公共队友端点**。

- **典型归属形态**：早期可由项目发起人的 `HumanID` 直接创建并持有；当项目发展成熟并捐赠给开源基金会或转入正式课题组时，可通过双签原子过户（`TransferEnvelope` 1.0）平滑移交至基金会的 `OrganizationID`，无需更改任何外部调用方已配置的 `cofay_` 地址！
- **多协议协同优势**：天然适合结合 **交互对话协议（ICP）** 对设计文稿、论文或代码规范产出结构化 `.ctx` 批注，并通过 **心灵感应协议（TP）** 与多位贡献者的个人 `iFay` 建立受限共享工作空间（详见 `Interactive-Conversation-Protocol` 与 `Telepathy-Protocol`）。

### 典型落地场景：跨机构科研与开源协议一致性协作单元
一个多语种开放协议工作组创建了 `cofay_ossprojectbot234567`（原型为 `project_collaborator`）。来自全球不同时区的贡献者无需等待维护者在线，其各自的 `iFay` 即可直接连接该协作单元：自动运行协议测试向量预检、核对九语种术语一致性，并将结构化审阅意见以 `.ctx` 批注形式反馈给贡献者；当该协作单元的高质量审阅获得社区认可时，相应的非货币**美誉值（MeriToken）**持续记入该项目协作单元的 `MeritPocket`，精准反映专项工程的公共贡献。

## 3.5 三大角色原型能力配置速查表

| 特征维度 | `org_service` | `functional_post` | `project_collaborator` |
|----------|---------------|-------------------|------------------------|
| **首要设计目标** | 高并发标准化公众/客户服务受理 | 权责严明的常设治理、审批与合规见证 | 专项知识聚合、多方研发协同与可移交演进 |
| **常见归属主体** | `OrganizationID`（或个体执业 `HumanID`） | `OrganizationID`（强制挂自然人主理人） | 初期常为 `HumanID`，成熟期常过户至 `OrganizationID` |
| **SSP 技能可见性** | `public` + `restricted` 组合为主 | `restricted` / `private` 强制鉴权为主 | `public`（开放协作）或 `restricted`（成员协作） |
| **CAP 最高自主等级** | `assistive` / `delegated` | `delegated` / `official_post` | `assistive` / `delegated` |
| **典型轮换/流转事件** | 后台运维班组 `managers` 轮换 | 席位主理人换届（`cofay_` 不变） | 从个人发起人向基金会组织的双签过户 |
