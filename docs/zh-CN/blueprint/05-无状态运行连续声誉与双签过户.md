# 05. 无状态运行、连续声誉与双签过户

## 5.1 破解核心张力：「无状态可替换实例」如何拥有「连续贡献账户」

在设计公共角色化身时，工程实践往往会遇到一组表面看似矛盾的需求：
- **从高可用服务视角看**：一个面向全网提供技能协作的 `coFay` 必须支持无状态水平扩缩容、跨机房故障切换与容器热升级——任何单个运行时进程挂掉或被替换，都不应影响外部调用；
- **从社会信誉积累视角看**：**公誉链（GMChain）** 为每一个 `cofay_<base32>` 唯一绑定了一个独立的 `MeritPocket`（美誉值口袋，详见 `Global-Merit-Chain`），用于长期累积该角色提供高质量公共服务所获得的**美誉值（MeriToken，最小单位 `μ` / Merit Unit）**与社区治理权重。

一个随时可以销毁重建的无状态进程，怎么可能拥有跨越数年的连续声誉账户？

`coFay` 通过**「执行弹性下沉运行层、身份与声誉锚定身份层」**的分层架构彻底化解了这一张力：

```text
                    ┌──────────────────────────────────────────┐
身份与账本层         │  唯一持久身份: cofay_orgservicedesk234567 │
（状态连续、不可篡改）│  1:1 绑定账本: GMChain MeritPocket (mpk_) │
                    │  治理契约锚点: RoleCharter 1.0 (JCS 签名) │
                    └────────────────────┬─────────────────────┘
                                         │ 统一加载同一份生效章程
                  ┌──────────────────────┼──────────────────────┐
                  ▼                      ▼                      ▼
运行执行层   [FayGer Worker #1]    [FayGer Worker #2]    [FayGer Worker #N]
（无状态弹性） 无自我层/随时扩缩     无自我层/热升级替换    异地容灾/按需唤醒
```

1. **运行层完全无状态（Stateless Runtime Elasticity）**：承载认知推理与协议解析的 **FayGer** 工作实例不在本地保存独占人格记忆（无自我层 Ego），仅在启动时加载经校验通过的当前生效版 `RoleCharter` 1.0 与只读领域知识包。流量激增时可秒级扩容至百个实例，流量回落时缩容归零。
2. **密码学代表签名统一归口**：多个无状态工作实例并非各自随意生成匿名响应，而是通过受硬件安全模块（HSM）/门限签名托管的 `cofay_` 持有者密钥（详见 `FayID`），或经由章程显式授权的 `managers: iFayID[]` 代表签名，向外部调用方与 `GMChain` 出具可验证回执。
3. **声誉归集于角色而非容器**：外部社会成员评价与认可的是 `cofay_` 这一公共角色的履职质量，产生的非货币 MeriToken 贡献记录全部归入与 `cofay_` 1:1 绑定的 `MeritPocket`——哪怕底层容器已经迭代升级了上百次，角色的公信力依然连续不断。

## 5.2 为什么所有权过户必须采用「双签原子协议」

与终身绑定唯一**人类原型（Human Prime）**的 `iFay` 不同，`coFay` 作为制度化角色资产天然存在合法移交需求：例如个人开发者发起的开源协作 `coFay`（`project_collaborator`）成熟后正式移交至开源基金会组织名下，或企业重组时某公共服务窗口从原事业部法人移交至新运营机构名下。

然而，若过户机制设计草率，立刻会引爆三大安全漏洞：
1. **单方强夺或恶意甩锅漏洞**：若只要求一方签名，攻击者要么能窃取他人角色，要么能把一个背负合规争议或声誉惩罚风险的 `coFay` 强行塞给不知情的第三方自然人或组织担责；
2. **前任管理代理残留漏洞（Stale Manager Retention）**：过户前，原归属方通常配置了若干内部运维 `managers: iFayID[]`。若过户时默认保留原有 `managers` 列表、留待新归属方事后手动清理，在交接瞬间就会出现危险的时间窗——原归属方的 `iFay` 仍能以已易主的 `coFay` 名义继续对外签发指令！
3. **历史过户信封重放漏洞（Replay Attack）**：若缺乏严格单调递增的防重放序号与前置章程摘要绑定，历史过户报文可能被恶意重放以回滚所有权。

## 5.3 `TransferEnvelope` 1.0：双签原子所有权过户规范流程

为根除上述三大隐患，`coFay` 定义了规范化的原子过户信封 **`TransferEnvelope` 1.0**（内嵌于 `schemas/cofay-role-charter-1.0.json` 的 `$defs.TransferEnvelope`）：

### 第一步：锁定前置状态与防重放序号
构造过户信封时，必须显式写入：
- `prior_charter_digest_hex`：当前生效版 `RoleCharter` 经 RFC 8785 JCS 规范化后的 SHA-256 十六进制摘要（不匹配立即拒绝并返回 `PRIOR_CHARTER_DIGEST_MISMATCH`）；
- `transfer_nonce`：严格等于 `currentCharter.transfer_nonce + 1`（任何重放旧序号或跳号均触发 `TRANSFER_NONCE_MISMATCH`）；
- `from_owner` 与 `to_owner`：双方均须符合单层归属约束（仅限 `HumanID` 或 `OrganizationID`，严禁 `ifay_` / `cofay_` 嵌套，且严禁自转给自己 `SELF_TRANSFER_REDUNDANT`）；若接收方 `to_owner.type === "organization"`，还必须同步指定接收方自然人主理人 `new_steward_human_id`。

### 第二步：强制执行前任管理代理清理或显式重审（`manager_policy`）
`TransferEnvelope` 1.0 **绝不允许静默继承前任 `managers`**，必须二选一声明：
- **`"CLEAR_ALL"`（默认安全推荐）**：`ratified_managers` 必须为空数组 `[]`，过户生效瞬间原有一切 `iFay` 管理代理权限原子归零；
- **`"RATIFY_NEW"`（零停机平滑接管）**：在 `ratified_managers` 中显式列出由接收方认可的新任 `iFay` 管理代理名单；由于整个过户信封受接收方签名覆盖，只有经接收方显式背书的 `iFay` 才能留任，前任未获追认的代理一律原子剔除。

### 第三步：让出方与接收方双向 Ed25519 联合签名
去除签名块后的过户载荷经 RFC 8785 JCS 序列化，并拼接域分离前缀 `"ifay.cofay.ownership-transfer.v1\0"` 后，必须**同时**收集两枚有效 Ed25519 签名：
- `from_signature`：由当前 `owner.id` 或当前 `steward_human_id` 签署；
- `to_signature`：由新任 `to_owner.id` 或新任 `new_steward_human_id` 签署。

缺失任一方签名立即返回 `TRANSFER_DUAL_SIGNATURE_REQUIRED`；任一方密钥伪造或载荷被篡改立即返回 `TRANSFER_SIGNATURE_INVALID`。

## 5.4 `MeritPocket` 无折损延续与失能保全冻结

### 1. 角色延续下的 `MeritPocket` 零继承折损
在 `GMChain` 的设计中，自然人去世后若向亲友移交个体声誉，必须按链上事前登记的社会关系亲密度执行严格的五档继承折损（亲密度不足 `0.1` 甚至禁止继承），以防止个人声誉买卖；但对于 `coFay` 的合规双签过户，`MeritPocket` 绑定的是 **`cofay_` 公共角色本身**而非前任归属个人。只要 `merit_continuity` 保持 `{ "preserve_cofay_id": true, "preserve_merit_pocket": true }`，该公共角色历史积累的 MeriToken 随角色完整延续至新归属主体责任监管之下，不触发自然人遗产折损（详见 `Global-Merit-Chain`）。当然，MeriToken 本身依然严格遵守随时间自然衰减并收敛至底值的非货币规律——任何组织都无法靠收购角色来永久囤积静态特权，唯有持续提供优质公共服务才能维持角色美誉度。

### 2. 组织注销或主理人失能时的保全冻结（`SUSPENDED_PENDING_SUCCESSION`）
如果某个归属组织发生主体注销，或者其登记的自然人主理人突发失能，且在事前尚未完成双签移交，该 `coFay` 会发生什么？
依据跨仓一致规则（对齐 `FayID` ADR `0003`）：
- 该 `coFay` **绝不会静默上卷**归属于母组织，也**不会变成无人担责的失控代理**，更不会立即销毁历史公誉记录；
- 其 `lifecycle_state` 将转入 **`"SUSPENDED_PENDING_SUCCESSION"`（待继承保全冻结态）**：在此状态下，禁止增删日常管理代理（`CHARTER_NOT_ACTIVE`），暂停对外签发新的受限业务动作；
- 直至依据预设门限治理恢复策略或完成合法的 `TransferEnvelope` 1.0 双签接管后，其状态方可重新激活为 `"ACTIVE"` 并恢复履职。
