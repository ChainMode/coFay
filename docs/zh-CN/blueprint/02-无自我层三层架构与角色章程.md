# 02. 无自我层三层架构与角色章程

## 2.1 四层架构在 coFay 上的精确剪裁

在伞仓库 `ifay` 确立的标准四层架构——**社交层（Social Layer）**、**交互层（Interaction Layer）**、**认知层（Cognition Layer）**与**自我层（Ego Layer）**——之中，两类数字化身呈现出清晰的结构性分野：`iFay` 完整具备全部四层，而 **`coFay` 仅由社交层、交互层与认知层三层构成，明确剪裁并严禁挂载自我层（Ego Layer）**。

```text
┌─────────────────────────────────────────────────────────────┐
│  [ 已剪裁 / 严禁挂载 ] 自我层（Ego Layer）                  │
│  × 不复刻自然人性格记忆   × 不加载 @ego-models/* 人格包     │
├─────────────────────────────────────────────────────────────┤
│  治理顶盖：规范角色章程 RoleCharter 1.0（Ed25519 + JCS）     │
│  ✓ 使命声明  ✓ SSP/CAP 权限上界  ✓ 红线禁令  ✓ 审计策略     │
├─────────────────────────────────────────────────────────────┤
│  第 3 层：认知层（Cognition Layer）                         │
│  · 领域知识推理与工作流编排   · 制度规则与技能路由决策       │
├─────────────────────────────────────────────────────────────┤
│  第 2 层：交互层（Interaction Layer）                       │
│  · 结构化对话（ICP）与心灵感应协作（TP）  · CAP 宿主受控操作 │
├─────────────────────────────────────────────────────────────┤
│  第 1 层：社交层（Social Layer）                            │
│  · cofay_ 身份与凭证管理  · SSP 技能发布  · GMChain 声誉口袋 │
└─────────────────────────────────────────────────────────────┘
```

为什么 `coFay` 绝不能拥有自我层？原因并非技术上无法挂载微调小模型，而是由三道不可妥协的治理准则决定的：

1. **防止人格拟真误导公众**：自我层（详见 `Ego`）的唯一使命是复刻某位真实**人类原型（Human Prime）**的价值偏好、情感习惯与私人记忆。如果一个公共服务窗口或法定审批席位加载了某位自然人的私人 Ego 模型，不仅会把个人偏见悄悄混入公共裁量，还会让外部交互者误以为自己正在与该自然人本人私下对话。
2. **保障多实例无状态一致性**：公共角色往往需要同时响应成千上万路并发协作请求。若依赖带有主观情绪漂移或局部私有记忆的自我层，不同工作实例对同一公共规则就会给出前后矛盾的响应；剪裁掉自我层后，所有实例统一受控于同一份确定性的角色章程与领域知识库。
3. **确保角色过户时的隐私零泄露**：`coFay` 作为制度资产支持跨归属主体移交。倘若其内部嵌有任何前任主理人或操作员的个人自我层切片，所有权过户就会演变成灾难性的个人隐私泄露。因此，校验器一旦检测到 `ego_package`、`ego_model`、`ego_profile`、`human_prime_id` 或 `personal_persona` 字段，立即触发 `COFAY_EGO_FORBIDDEN` 硬拦截。

## 2.2 三层运行时的职能分工

在剥离自我层之后，`coFay` 的三层架构围绕「履行公共章程」紧密协同：

### 1. 社交层（Social Layer）：公共身份、凭证与协作契约门面
社交层负责管理 `coFay` 在生态社会网络中的可验证身份与对外服务声明：
- 持有并保护 `cofay_<base32>` 身份标识及其关联校验凭证（详见 `FayID`）；
- 通过 **技能共享协议（SSP）** 对外暴露带有 `cofay_` JWS 签名的技能描述符（详见 `Skill-Sharing-Protocol`），明确区分 `public`（公开免登查询）、`restricted`（受限合作方鉴权调用）与 `private`（内部管理调用）三档可见性；
- 维护与 **公誉链（GMChain）** 上一对一绑定 `MeritPocket` 的记账映射引用（`gmc_merit_pocket_ref`），忠实记录该公共角色提供社会化协作所获得的非货币**美誉值（MeriToken）**（详见 `Global-Merit-Chain`）。

### 2. 交互层（Interaction Layer）：多模态接入与受控宿主动作
交互层定义了外部世界与 `coFay` 沟通及 `coFay` 驱动终端宿主（Host，仅指终端硬件设备或软件应用）的标准化通道：
- **入站协议交互**：支持基于 **交互对话协议（ICP）** 的富上下文结构化批注交互（详见 `Interactive-Conversation-Protocol`），以及基于 **心灵感应协议（TP）** 的高带宽跨 Fay 目标协同与咨询会话（详见 `Telepathy-Protocol`）；
- **出站宿主控制**：当公共角色需要操作业务软件队列、传感器或专用终端宿主时，必须严格在 `RoleCharter.allowed_capabilities.cap_bounds` 限定的作用域内，通过 **控制权限协议（CAP）** 与 **数据隧道协议（DTP）** 执行受审计动作（详见 `Control-Authority-Protocol` 与 `Data-Tunnel-Protocol`），不得越权触碰未声明的宿主资源。

### 3. 认知层（Cognition Layer）：章程约束下的领域推理与技能编排
认知层是 `coFay` 处理专业领域任务的核心引擎，可在 **FayGer** 容器运行时中按声明式配置弹性装配（详见 `FayGer`）：
- 加载与特定角色匹配的行业法规库、项目架构索引或标准作业程序（SOP）；
- 在每次生成外部承诺或触发外部动作前，执行**章程前置策略核验（Charter Policy Gate）**：比对 `allowed_capabilities` 白名单与 `prohibited_actions` 红线列表；凡触及红线或超出 `max_autonomy_tier`（如 `allow_irreversible_actions: false` 时的不可逆变更），认知层必须挂起执行并上报人类主理人或其授权的 `iFay` 管理代理。

## 2.3 `RoleCharter` 1.0：替代自我层的制度化宪法

如果说 `Ego` 模型回答了 `iFay`「我是谁的复刻、我秉持怎样的人格品味」，那么 **`RoleCharter` 1.0（规范 Schema ID：`https://ifay.ai/schemas/cofay-role-charter-1.0.json`）**就回答了 `coFay`「我承担什么公共职责、归谁所有、谁来担责、能做什么、绝不能做什么」。

一份完整的 `RoleCharter` 1.0 由五大核心结构块组成：

### （1）身份与版本元数据块
- `schema_version`：固定为两段式 `"1.0"`；
- `charter_id`（`chr_<base32>`）与单调递增正整数 `charter_revision`：确保章程每次修订都有唯一版本锚点；
- `cofay_id`（`cofay_<base32>`）、`display_name` 与 `role_archetype`（三大规范角色原型之一）；
- `lifecycle_state`：显式标注 `"ACTIVE"`、`"SUSPENDED_PENDING_SUCCESSION"`（待继承保全冻结）或 `"REVOKED"`（永久撤销）；
- `transfer_nonce`：初始为 `0`，仅随合法双签所有权过户严格单调加 `1`。

### （2）权责锚定与正交委托块
- `owner`：单层归属引用（`human` 对应 `hid_<base32>`，或 `organization` 对应 `org_<slug|base32>`）；
- `steward_human_id`：当 `owner.type === "organization"` 时必填的自然人主理人 `hid_<base32>`，确保组织责任穿透到具体自然人；
- `managers`：零个或多个正交运营委托代理人 `ifay_<base32>[]`。

### （3）使命声明、能力白名单与行为红线块
- `mission_statement`：面向公众与调用方披露的职责范围说明；
- `allowed_capabilities.ssp_skills`：逐项声明对外暴露的技能 URI、可见性级别与调用端鉴权开关。规范硬性规定：凡 `visibility` 为 `"restricted"` 或 `"private"` 的技能，`require_caller_auth` **必须**为 `true`（否则触发 `SSP_AUTH_REQUIRED_FOR_NON_PUBLIC`），绝不允许仅靠目录隐藏代替端点鉴权；
- `allowed_capabilities.cap_bounds`：限定允许请求的 CAP 权限作用域（`allowed_scopes`）、最高自主等级（`assistive` / `delegated` / `official_post`）及是否允许不可逆动作（`allow_irreversible_actions`）；
- `prohibited_actions`：非空红线数组，将业务合规禁令固化为机器可读契约。

### （4）本地自足审计策略块（`audit_policy`）
- 规定审计日志保留天数（`retention_days`）、防篡改存储模式（`hash_chain` 哈希链或 `append_only` 只追加日志）以及强制开启的 `require_actor_trace: true`；
- 每条对外代表动作记录都必须落地 `(cofay_id, owner_id, actor_signer_id)` 三元组，且严禁将 `acting_as_natural_person` 置为真值（违者触发 `NATURAL_PERSON_IMPERSONATION_FORBIDDEN`）。即使在完全离线的局域网环境中，审计链条依然完整可验。

### （5）RFC 8785 JCS + Ed25519 归属签名块（`owner_signature`）
为消除不同语言 JSON 序列化键序差异带来的验签歧义，`RoleCharter` 1.0 规定：去除 `owner_signature` 后的章程对象须先经 **RFC 8785 JSON Canonicalization Scheme（JCS）** 生成唯一确定性的 UTF-8 字节串，再前置域分离标签 `"ifay.cofay.role-charter.v1\0"`，最后由 `owner.id` 或 `steward_human_id` 对应的 Ed25519 私钥签名。任何字段哪怕改动一个字符，都会立即导致 `CHARTER_SIGNATURE_INVALID` 验签失败。
