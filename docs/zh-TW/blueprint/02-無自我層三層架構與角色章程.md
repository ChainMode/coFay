# 02. 無自我層三層架構與角色章程

## 2.1 四層架構在 coFay 上的精確裁剪

在傘型儲存庫 `ifay` 確立的標準四層架構，即**社交層（Social Layer）**、**互動層（Interaction Layer）**、**認知層（Cognition Layer）**與**自我層（Ego Layer）**之中，兩類數位化身呈現出清晰的結構性分野：`iFay` 完整具備全部四層，而 **`coFay` 僅由社交層、互動層與認知層三層構成，明確裁剪並嚴禁掛載自我層（Ego Layer）**。

```text
┌─────────────────────────────────────────────────────────────┐
│  [ 已裁剪 / 嚴禁掛載 ] 自我層（Ego Layer）                  │
│  × 不復刻自然人性格記憶   × 不載入 @ego-models/* 人格套件   │
├─────────────────────────────────────────────────────────────┤
│  治理頂蓋：規範角色章程 RoleCharter 1.0（Ed25519 + JCS）     │
│  ✓ 使命聲明  ✓ SSP/CAP 權限上界  ✓ 紅線禁令  ✓ 稽核策略     │
├─────────────────────────────────────────────────────────────┤
│  第 3 層：認知層（Cognition Layer）                         │
│  · 領域知識推理與工作流程編排 · 制度規則與技能路由決策       │
├─────────────────────────────────────────────────────────────┤
│  第 2 層：互動層（Interaction Layer）                       │
│  · 結構化對話（ICP）與心靈感應協作（TP） · CAP 宿主受控操作 │
├─────────────────────────────────────────────────────────────┤
│  第 1 層：社交層（Social Layer）                            │
│  · cofay_ 身分與憑證管理  · SSP 技能發布  · GMChain 聲譽口袋 │
└─────────────────────────────────────────────────────────────┘
```

為什麼 `coFay` 絕不能擁有自我層？原因並非技術上無法掛載微調小型模型，而是由三道不可妥協的治理準則所決定：

1. **防止人格擬真誤導公眾**：自我層（詳見 `Ego`）的唯一使命是復刻某位真實**人類原型（Human Prime）**的價值偏好、情感習慣與私人記憶。如果一個公共服務窗口或法定審查席位載入了某位自然人的私人 Ego 模型，不僅會把個人偏見悄悄混入公共裁量，還會讓外部互動者誤以為自己正在與該自然人本人私下對話。
2. **保障多執行個體無狀態一致性**：公共角色往往需要同時回應成千上萬路並行協作請求。若仰賴帶有主觀情緒漂移或局部私有記憶的自我層，不同工作執行個體面對同一條公共規則就會給出前後矛盾的回應；裁剪掉自我層後，所有執行個體皆統一受控於同一份確定性的角色章程與領域知識庫。
3. **確保角色過戶時的隱私零外洩**：`coFay` 作為制度資產支援跨歸屬主體移交。倘若其內部嵌有任何前任主理人或作業人員的個人自我層切片，所有權過戶就會演變成災難性的個人隱私外洩。因此，檢核器一旦偵測到 `ego_package`、`ego_model`、`ego_profile`、`human_prime_id` 或 `personal_persona` 欄位，便會立即觸發 `COFAY_EGO_FORBIDDEN` 硬性攔截。

## 2.2 三層執行時期的職能分工

在剝離自我層之後，`coFay` 的三層架構圍繞「履行公共章程」緊密協同運作：

### 1. 社交層（Social Layer）：公共身分、憑證與協作契約門面
社交層負責管理 `coFay` 在生態社會網路中的可驗證身分與對外服務聲明：
- 持有並保護 `cofay_<base32>` 身分識別碼及其關聯檢核憑證（詳見 `FayID`）；
- 透過 **技能共享協定（SSP）** 對外公開帶有 `cofay_` JWS 簽章的技能描述符（詳見 `Skill-Sharing-Protocol`），明確區分 `public`（公開免驗證查詢）、`restricted`（受限合作方驗證呼叫）與 `private`（內部管理呼叫）三種可見度等級；
- 維護與 **公譽鏈（GMChain）** 上一對一綁定 `MeritPocket` 的記帳映射參照（`gmc_merit_pocket_ref`），忠實記錄該公共角色提供社會化協作所獲得的非貨幣**美譽值（MeriToken）**（詳見 `Global-Merit-Chain`）。

### 2. 互動層（Interaction Layer）：多模態接入與受控宿主動作
互動層定義了外部世界與 `coFay` 溝通，以及 `coFay` 驅動終端宿主（Host，僅指終端硬體裝置或軟體應用）的標準化通道：
- **入站協定互動**：支援基於 **互動對話協定（ICP）** 的富脈絡結構化批註互動（詳見 `Interactive-Conversation-Protocol`），以及基於 **心靈感應協定（TP）** 的高頻寬跨 Fay 目標協同與諮詢工作階段（詳見 `Telepathy-Protocol`）；
- **出站宿主控制**：當公共角色需要操作業務軟體佇列、感測器或專用終端宿主時，必須嚴格在 `RoleCharter.allowed_capabilities.cap_bounds` 限定的作用範圍內，透過 **控制權限協定（CAP）** 與 **資料通道協定（DTP）** 執行受稽核動作（詳見 `Control-Authority-Protocol` 與 `Data-Tunnel-Protocol`），不得越權觸碰未宣告的宿主資源。

### 3. 認知層（Cognition Layer）：章程約束下的領域推理與技能編排
認知層是 `coFay` 處理專業領域任務的核心引擎，可在 **FayGer** 容器執行環境中依宣告式組態彈性裝配（詳見 `FayGer`）：
- 載入與特定角色相符的產業法規庫、專案架構索引或標準作業程序（SOP）；
- 在每次產出外部承諾或觸發外部動作前，執行**章程前置策略檢核（Charter Policy Gate）**：比對 `allowed_capabilities` 白名單與 `prohibited_actions` 紅線清單；凡觸及紅線或超出 `max_autonomy_tier`（例如在 `allow_irreversible_actions: false` 時嘗試執行不可逆變更），認知層必須暫停執行並上報人類主理人或其授權的 `iFay` 管理代理。

## 2.3 `RoleCharter` 1.0：替代自我層的制度化憲法

如果說 `Ego` 模型回答了 `iFay`「我是誰的復刻、我秉持怎樣的人格品味」，那麼 **`RoleCharter` 1.0（規範 Schema ID：`https://ifay.ai/schemas/cofay-role-charter-1.0.json`）** 就回答了 `coFay`「我承擔什麼公共職責、歸誰所有、誰來負責、能做什麼、絕不能做什麼」。

一份完整的 `RoleCharter` 1.0 由五大核心結構區塊組成：

### （1）身分與版本中繼資料區塊
- `schema_version`：固定為兩段式 `"1.0"`；
- `charter_id`（`chr_<base32>`）與單調遞增正整數 `charter_revision`：確保章程每次修訂皆具備唯一版本錨點；
- `cofay_id`（`cofay_<base32>`）、`display_name` 與 `role_archetype`（三大規範角色原型之一）；
- `lifecycle_state`：明確標註 `"ACTIVE"`、`"SUSPENDED_PENDING_SUCCESSION"`（待繼承保全凍結）或 `"REVOKED"`（永久撤銷）；
- `transfer_nonce`：初始值為 `0`，僅隨合法雙簽所有權過戶嚴格單調加 `1`。

### （2）權責錨定與正交委託區塊
- `owner`：單層歸屬參照（`human` 對應 `hid_<base32>`，或 `organization` 對應 `org_<slug|base32>`）；
- `steward_human_id`：當 `owner.type === "organization"` 時必填的自然人主理人 `hid_<base32>`，確保組織責任穿透至具體自然人；
- `managers`：零個或多個正交維運委託代理人 `ifay_<base32>[]`。

### （3）使命聲明、能力白名單與行為紅線區塊
- `mission_statement`：面向公眾與呼叫端揭露的職責範圍說明；
- `allowed_capabilities.ssp_skills`：逐項宣告對外公開的技能 URI、可見度等級與呼叫端身分驗證開關。規範硬性規定：凡 `visibility` 為 `"restricted"` 或 `"private"` 的技能，`require_caller_auth` **必須**設為 `true`（否則觸發 `SSP_AUTH_REQUIRED_FOR_NON_PUBLIC`），絕不允許僅靠目錄隱藏來取代端點權限驗證；
- `allowed_capabilities.cap_bounds`：限定允許請求的 CAP 權限作用範圍（`allowed_scopes`）、最高自主等級（`assistive` / `delegated` / `official_post`），以及是否允許不可逆動作（`allow_irreversible_actions`）；
- `prohibited_actions`：非空紅線陣列，將業務合規禁令固化為機器可讀契約。

### （4）本機自足稽核策略區塊（`audit_policy`）
- 規範稽核日誌保留天數（`retention_days`）、防竄改儲存模式（`hash_chain` 雜湊鏈或 `append_only` 僅追加日誌），以及強制啟用的 `require_actor_trace: true`；
- 每筆對外代表動作紀錄都必須寫入 `(cofay_id, owner_id, actor_signer_id)` 三元組，且嚴禁將 `acting_as_natural_person` 設為真值（違者觸發 `NATURAL_PERSON_IMPERSONATION_FORBIDDEN`）。即使在完全離線的區域網路環境中，稽核鏈路依然完整可驗。

### （5）RFC 8785 JCS + Ed25519 歸屬簽章區塊（`owner_signature`）
為消除不同程式語言 JSON 序列化鍵值順序差異所帶來的驗章歧義，`RoleCharter` 1.0 規定：移除 `owner_signature` 後的章程物件須先經由 **RFC 8785 JSON Canonicalization Scheme（JCS）** 產出唯一確定性的 UTF-8 位元組串，再前置網域分離標籤 `"ifay.cofay.role-charter.v1\0"`，最後由 `owner.id` 或 `steward_human_id` 對應的 Ed25519 私鑰簽章。任何欄位哪怕僅更動一個字元，都會立即導致 `CHARTER_SIGNATURE_INVALID` 驗章失敗。
