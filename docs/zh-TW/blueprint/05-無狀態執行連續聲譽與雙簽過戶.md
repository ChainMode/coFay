# 05. 無狀態執行、連續聲譽與雙簽過戶

## 5.1 破解核心張力：「無狀態可替換執行個體」如何擁有「連續貢獻帳戶」

在設計公共角色化身時，工程實務往往會遇到一組表面看似矛盾的需求：
- **從高可用性服務視角來看**：一個針對全網提供技能協作的 `coFay` 必須支援無狀態水平擴縮、跨機房故障轉移（Failover）與容器熱升級；任何單一執行時期程序異常中斷或被替換，都不應影響外部呼叫；
- **從社會信譽累積視角來看**：**公譽鏈（GMChain）** 為每一個 `cofay_<base32>` 唯一綁定了一個獨立的 `MeritPocket`（美譽值口袋，詳見 `Global-Merit-Chain`），用於長期累積該角色提供高品質公共服務所獲得的**美譽值（MeriToken，最小單位 `μ` / Merit Unit）**與社群治理權重。

一個隨時可以銷毀重建的無狀態程序，怎麼可能擁有跨越數年的連續聲譽帳戶？

`coFay` 透過**「執行彈性下沉至執行層、身分與聲譽錨定於身分層」**的分層架構，徹底化解了這道張力：

```text
                    ┌──────────────────────────────────────────┐
身分與帳本層         │  唯一持久身分: cofay_orgservicedesk234567 │
（狀態連續、不可竄改）│  1:1 綁定帳本: GMChain MeritPocket (mpk_) │
                    │  治理契約錨點: RoleCharter 1.0 (JCS 簽章) │
                    └────────────────────┬─────────────────────┘
                                         │ 統一載入同一份生效章程
                  ┌──────────────────────┼──────────────────────┐
                  ▼                      ▼                      ▼
執行時期層   [FayGer Worker #1]    [FayGer Worker #2]    [FayGer Worker #N]
（無狀態彈性） 無自我層/隨時擴縮     無自我層/熱升級替換    異地備援/依需喚醒
```

1. **執行層完全無狀態（Stateless Runtime Elasticity）**：承載認知推理與協定剖析的 **FayGer** 工作執行個體不在本機保存獨占人格記憶（無自我層 Ego），僅在啟動時載入經檢核通過的當前生效版 `RoleCharter` 1.0 與唯讀領域知識套件。流量暴增時可於秒級擴展至上百個執行個體，流量回落時則可縮減歸零。
2. **密碼學代表簽章統一歸口**：多個無狀態工作執行個體並非各自隨意產出匿名回應，而是透過受硬體安全模組（HSM）或門檻簽章託管的 `cofay_` 持有者金鑰（詳見 `FayID`），或經由章程明確授權的 `managers: iFayID[]` 代表簽章，向外部呼叫端與 `GMChain` 出具可驗證回執。
3. **聲譽歸集於角色而非容器**：外部社會成員評價與認可的是 `cofay_` 這個公共角色的履職品質，產生的非貨幣 MeriToken 貢獻紀錄全部歸入與 `cofay_` 1:1 綁定的 `MeritPocket`；哪怕底層容器已經迭代升級了上百次，角色的公信力依然連續不斷。

## 5.2 為什麼所有權過戶必須採用「雙簽原子協定」

與終身綁定唯一**人類原型（Human Prime）**的 `iFay` 不同，`coFay` 作為制度化角色資產天生存在合法移交需求：例如個人開發者發起的開源協作 `coFay`（`project_collaborator`）成熟後正式移交至開源基金會組織名下，或是企業組織重整時，某個公共服務窗口從原事業部法人移交至新營運機構名下。

然而，若過戶機制設計草率，立刻會引爆三大資安漏洞：
1. **單方強奪或惡意卸責漏洞**：若只要求單方簽章，攻擊者不是能竊取他人角色，就是能把一個背負合規爭議或聲譽懲罰風險的 `coFay` 強行塞給不知情的第三方自然人或組織承擔責任；
2. **前任管理代理殘留漏洞（Stale Manager Retention）**：過戶前，原歸屬方通常組態了若干內部維運 `managers: iFayID[]`。若過戶時預設保留原有 `managers` 清單、留待新歸屬方事後手動清除，在交接瞬間就會出現危險的時間窗，讓原歸屬方的 `iFay` 仍能以已易主的 `coFay` 名義繼續對外簽發指令；
3. **歷史過戶信封重放漏洞（Replay Attack）**：若缺乏嚴格單調遞增的防重放序號與前置章程摘要綁定，歷史過戶封包就可能遭惡意重放以回滾所有權。

## 5.3 `TransferEnvelope` 1.0：雙簽原子所有權過戶規範流程

為根除上述三大隱憂，`coFay` 定義了規範化的原子過戶信封 **`TransferEnvelope` 1.0**（內嵌於 `schemas/cofay-role-charter-1.0.json` 的 `$defs.TransferEnvelope`）：

### 第一步：鎖定前置狀態與防重放序號
建構過戶信封時，必須明確寫入：
- `prior_charter_digest_hex`：當前生效版 `RoleCharter` 經 RFC 8785 JCS 正規化後的 SHA-256 十六進位摘要（不相符將立即拒絕並回傳 `PRIOR_CHARTER_DIGEST_MISMATCH`）；
- `transfer_nonce`：嚴格等於 `currentCharter.transfer_nonce + 1`（任何重放舊序號或跳號均觸發 `TRANSFER_NONCE_MISMATCH`）；
- `from_owner` 與 `to_owner`：雙方均須符合單層歸屬約束（僅限 `HumanID` 或 `OrganizationID`，嚴禁 `ifay_` / `cofay_` 巢狀持有，且嚴禁轉讓給自己 `SELF_TRANSFER_REDUNDANT`）；若接收方 `to_owner.type === "organization"`，還必須同步指定接收方自然人主理人 `new_steward_human_id`。

### 第二步：強制執行前任管理代理清理或明確重審（`manager_policy`）
`TransferEnvelope` 1.0 **絕不允許靜默繼承前任 `managers`**，必須擇一宣告：
- **`"CLEAR_ALL"`（預設安全建議）**：`ratified_managers` 必須為空陣列 `[]`，過戶生效瞬間原有一切 `iFay` 管理代理權限原子歸零；
- **`"RATIFY_NEW"`（零停機平滑接管）**：在 `ratified_managers` 中明確列出經接收方認可的新任 `iFay` 管理代理名單；由於整個過戶信封受接收方簽章涵蓋，唯有經接收方明確背書的 `iFay` 才能留任，前任未獲追認的代理一律原子剔除。

### 第三步：讓出方與接收方雙向 Ed25519 聯合簽章
移除簽章區塊後的過戶負載經 RFC 8785 JCS 序列化，並串接網域分離前綴 `"ifay.cofay.ownership-transfer.v1\0"` 後，必須**同時**備妥兩枚有效 Ed25519 簽章：
- `from_signature`：由當前 `owner.id` 或當前 `steward_human_id` 簽署；
- `to_signature`：由新任 `to_owner.id` 或新任 `new_steward_human_id` 簽署。

缺少任一方簽章立即回傳 `TRANSFER_DUAL_SIGNATURE_REQUIRED`；任一方金鑰偽造或負載遭竄改則立即回傳 `TRANSFER_SIGNATURE_INVALID`。

## 5.4 `MeritPocket` 無折損延續與失能保全凍結

### 1. 角色延續下的 `MeritPocket` 零繼承折損
在 `GMChain` 的設計中，自然人過世後若向親友移交個體聲譽，必須依鏈上事前登記的社會關係親密度執行嚴格的五級繼承折損（親密度不足 `0.1` 甚至禁止繼承），以防止個人聲譽買賣；但對於 `coFay` 的合規雙簽過戶，`MeritPocket` 綁定的是 **`cofay_` 公共角色本身**而非前任歸屬個人。只要 `merit_continuity` 維持 `{ "preserve_cofay_id": true, "preserve_merit_pocket": true }`，該公共角色歷史累積的 MeriToken 便會隨角色完整延續至新歸屬主體的責任監管之下，不觸發自然人遺產折損（詳見 `Global-Merit-Chain`）。當然，MeriToken 本身依然嚴格遵守隨時間自然衰減並收斂至底值的非貨幣規律，任何組織都無法靠收購角色來永久囤積靜態特權，唯有持續提供優質公共服務才能維持角色美譽度。

### 2. 組織註銷或主理人失能時的保全凍結（`SUSPENDED_PENDING_SUCCESSION`）
如果某個歸屬組織發生主體註銷，或是其登記的自然人主理人突發失能，且在事前尚未完成雙簽移交，該 `coFay` 會發生什麼事？
依據跨儲存庫一致規則（對齊 `FayID` ADR `0003`）：
- 該 `coFay` **絕不會靜默上捲**歸屬於母組織，也**不會變成無人負責的失控代理**，更不會立即銷毀歷史公譽紀錄；
- 其 `lifecycle_state` 將轉入 **`"SUSPENDED_PENDING_SUCCESSION"`（待繼承保全凍結態）**：在此狀態下，禁止新增或移除日常管理代理（`CHARTER_NOT_ACTIVE`），並暫停對外簽發新的受限業務動作；
- 直至依據預設門檻治理復原策略，或完成合法的 `TransferEnvelope` 1.0 雙簽接管後，其狀態方可重新啟用為 `"ACTIVE"` 並恢復履職。
