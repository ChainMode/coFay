# 03. 公共角色分類與應用場景

## 3.1 為什麼需要規範化的首期角色分類法

在現實社會中，「公共角色」橫跨政務受理、企業客服、合規稽核、科研協作與開源社群治理等無數垂直領域。如果 `RoleCharter` 1.0 完全不區分角色類型，或者反過來依上百個垂直產業寫死列舉值，都會帶來嚴重的工程問題：前者無法針對不同權責等級的角色設定差異化的預設安全基準；後者則會讓核心協定失去通用性與演進彈性。

為此，`coFay` 依據**「對外服務拓樸、裁量權邊界與席位生命週期」**三項正交特徵，確立了首期三大規範角色原型（`role_archetype`）：

1. **`org_service`（組織公共服務窗口）**
2. **`functional_post`（法定/治理職能席位）**
3. **`project_collaborator`（專案/專項協作單元）**

所有合法的 `RoleCharter` 1.0 文件都必須在 `role_archetype` 欄位中明確宣告上述三者之一（超出範圍將立即觸發 `ROLE_ARCHETYPE_INVALID`）。

## 3.2 原型一：`org_service`（組織公共服務窗口）

### 定位與核心特徵
`org_service` 代表企業、公共機構、產業公會或獨立服務提供者對外開設的**標準化諮詢、業務受理與技能服務門面**，也是外部呼叫端最常接觸的一類 `coFay`。

- **典型歸屬形態**：通常歸屬於 `OrganizationID`（例如 `org_civic-service-bureau`）並掛接自然人主理人 `steward_human_id`；獨立商號或個人執業工作室亦可直接歸屬於 `HumanID`。
- **CAP 自主等級建議**：通常組態為 `assistive` 或 `delegated`，並將 `allow_irreversible_actions` 設為 `false`；亦即允許自動完成資訊核驗、工單分派、預約排程與標準化技能回應，但涉及重大權益變更時，則轉交後台主理人或獲授權的 `iFay` 複核。
- **SSP 技能公開特徵**：往往混合公開免驗證的 `public` 申辦指南查詢技能，以及強制身分驗證（`require_caller_auth: true`）的 `restricted` 業務申辦技能。

### 典型落地場景：市政許可與公共諮詢窗口
某市行政服務局部署了一個市政許可服務窗口 `cofay_orgservicedesk234567`。市民無需翻找繁雜的機關申辦網頁，只需向自己的個人 `iFay` 發出指令：「幫我核對新開社區書店所需的消防與營業備查文件」。
1. 市民的 `iFay` 透過 **SSP** 探索並找到該政務 `coFay`，首先驗證其 `RoleCharter` 1.0 上的 `org_civic-service-bureau` 歸屬與主理人 Ed25519 簽章；
2. 確認無誤後，市民 `iFay` 呼叫公開查詢技能取得應備文件清單，並在取得人類原型明確授權後，透過受限受理技能送出預審資料包；
3. 政務 `coFay` 的後台可同時執行數十個無狀態工作執行個體以消化尖峰時段請求，所有預審回執皆附帶可稽核的 `(cofay_id, owner_id, actor_signer_id)` 紀錄。

## 3.3 原型二：`functional_post`（法定/治理職能席位）

### 定位與核心特徵
`functional_post` 代表組織內部、跨機構聯盟或生態基礎設施中**具有明確制度職權、核准職責或合規見證義務的常設職務席位**。它的核心理念是「鐵打的席位，流水的當值人」。

- **典型歸屬形態**：歸屬於治理委員會、基金會、企業內控部門等 `OrganizationID`，並強制綁定現任自然人主理人 `steward_human_id`。
- **與 CAP `Official_Post` 的語意銜接**：在 **控制權限協定（CAP）** 中，部分高敏感度裝置或關鍵基礎設施操作要求由公職或法定職務席位（`Official_Post`）簽發或會簽授權描述符（詳見 `Control-Authority-Protocol`）。`functional_post` 型 `coFay` 正是這項席位語意在角色層的規範承載者，其 `cap_bounds.max_autonomy_tier` 可宣告為 `"official_post"`。
- **人員輪調與聲譽連續性**：當某屆資安稽核官任期屆滿、新任稽核官接任時，組織只需更新該 `coFay` 的 `steward_human_id` 與日常執勤 `managers: iFayID[]`，並發布新修訂版號（`charter_revision + 1`）的 `RoleCharter`；席位本身的 `cofay_` 識別碼、外部訂閱參照以及鏈上 `MeritPocket` 歷史履職紀錄皆維持零中斷延續。

### 典型落地場景：公譽鏈生態資安稽核席與無人載具空域簽派席
- **生態治理合規稽核席**：某開源資安聯盟設立常設漏洞揭露與修補程式核驗席位 `cofay_govpostauditor234567`。各專案團隊將資安通報推送至該席位；值班資安專家透過各自獲授權的 `iFay` 管理代理驅動該席位完成重現檢核與簽章背書，所有外部系統只需信任該常設席位的公鑰鏈即可。
- **園區低空物流簽派席**：園區管委會設立空域航線簽派 `functional_post` `coFay`，透過 CAP / DTP 與配送機器人的終端宿主互動，在氣象異常時依據章程紅線自動下達禁飛停靠指令。

## 3.4 原型三：`project_collaborator`（專案/專項協作單元）

### 定位與核心特徵
`project_collaborator` 針對特定開源儲存庫、跨校科研計畫、標準工作小組或跨企業專項工程組建，作為**聚合領域知識圖譜、自動化工具鏈與協作工作流程的公共隊友端點**。

- **典型歸屬形態**：初期可由專案發起人的 `HumanID` 直接建立並持有；當專案發展成熟並捐贈予開源基金會或移交正式研究團隊時，可透過雙簽原子過戶（`TransferEnvelope` 1.0）平滑移交至基金會的 `OrganizationID`，完全無需更動任何外部呼叫端已設定的 `cofay_` 位址。
- **多協定協同優勢**：天生適合結合 **互動對話協定（ICP）** 對設計文稿、學術論文或程式碼規範產出結構化 `.ctx` 批註，並透過 **心靈感應協定（TP）** 與多位貢獻者的個人 `iFay` 建立受限共享工作空間（詳見 `Interactive-Conversation-Protocol` 與 `Telepathy-Protocol`）。

### 典型落地場景：跨機構科研與開源協定一致性協作單元
一個多語系開放協定工作小組建立了 `cofay_ossprojectbot234567`（原型為 `project_collaborator`）。來自全球不同時區的貢獻者無需等待維護者在線上，其各自的 `iFay` 即可直接連線至該協作單元：自動執行協定測試向量預檢、核對九語系術語一致性，並將結構化審閱意見以 `.ctx` 批註形式回饋給貢獻者；當該協作單元的高品質審閱獲得社群認可時，相應的非貨幣**美譽值（MeriToken）**便會持續記入該專案協作單元的 `MeritPocket`，精準反映專項工程的公共貢獻。

## 3.5 三大角色原型能力組態速查表

| 特徵維度 | `org_service` | `functional_post` | `project_collaborator` |
|----------|---------------|-------------------|------------------------|
| **首要設計目標** | 高並行標準化公眾/客戶服務受理 | 權責嚴明的常設治理、核准與合規見證 | 專項知識聚合、多方研發協同與可移交演進 |
| **常見歸屬主體** | `OrganizationID`（或獨立執業 `HumanID`） | `OrganizationID`（強制掛接自然人主理人） | 初期常為 `HumanID`，成熟期常過戶至 `OrganizationID` |
| **SSP 技能可見度** | `public` + `restricted` 組合為主 | `restricted` / `private` 強制驗證為主 | `public`（開放協作）或 `restricted`（成員協作） |
| **CAP 最高自主等級** | `assistive` / `delegated` | `delegated` / `official_post` | `assistive` / `delegated` |
| **典型輪調/流轉事件** | 後台維運班組 `managers` 輪調 | 席位主理人改選交接（`cofay_` 不變） | 從個人發起人移交至基金會組織的雙簽過戶 |
