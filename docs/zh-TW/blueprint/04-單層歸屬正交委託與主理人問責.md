# 04. 單層歸屬、正交委託與主理人問責

## 4.1 為什麼要把「歸屬權」「組織階層」與「日常管理權」徹底正交解耦

在大型分散式代理生態中，最危險的架構反模式之一，就是把「誰擁有這個代理」「組織上下級如何巢狀隸屬」與「今天誰獲授權操作這個代理」混壓在同一棵樹結構裡。如果允許一個 `coFay` 去擁有另一個 `coFay`，或者允許一個 `iFay` 作為 `coFay` 的法律歸屬所有者，很快就會衍生出深不見底的多跳空殼巢狀結構：既無法回答最終法律與社會問責落在哪位自然人或法人頭上，也會在代理權限變更時引發連鎖雪崩。

為此，`coFay` 與 **FayID**、**公譽鏈（GMChain）** 跨儲存庫統一執行**三條正交軸模型**（詳見 `FayID` 與 `Global-Merit-Chain`）：

1. **歸屬軸（Ownership Axis）**：回答「這個 `coFay` 的產權與最終責任屬於誰」，嚴格限制為**單層歸屬**；
2. **組織階層軸（Organization Hierarchy Axis）**：回答「集團母公司與子公司之間是什麼關係」，完全在 `OrganizationID` 自身的單親有根無環樹中表達，絕不借用 `coFay` 巢狀持有來模擬；
3. **日常管理委託軸（Operational Delegation Axis）**：回答「哪些個體化身獲授權在日常維運中代表該 `coFay` 執勤」，透過正交的 `managers: iFayID[]` 單跳授予，絕不改變歸屬主體。

## 4.2 單層歸屬鐵律與自然人主理人（Steward）穿透問責

在 `RoleCharter` 1.0 中，每個 `coFay` 在任意時間點有且僅有一個歸屬主體 `owner`：

- **個人直接歸屬**：`owner = { "type": "human", "id": "hid_<base32>" }`；
- **組織直接歸屬**：`owner = { "type": "organization", "id": "org_<slug|base32>" }`。

任何試圖將 `ifay_<base32>` 或 `cofay_<base32>` 填入 `owner.id` 的行為，都會在結構描述（Schema）層與執行時期檢核層同時遭到 `OWNER_TYPE_FORBIDDEN` 拒絕。即便歸屬組織 `org_sub` 在 `FayID` 中存在母組織 `org_parent`，該 `coFay` 的 `owner` 也只能精確填寫直接持有它的 `org_sub`，不會隱含上捲至母組織。

### 組織歸屬下的自然人主理人強制約束
組織是法律與協作上的抽象實體，無法親自保管實體硬體安全金鑰或獨立承擔自然人倫理審查義務。因此，`RoleCharter` 1.0 規定：

> **凡 `owner.type === "organization"` 的 `coFay`，必須明確宣告合法的自然人主理人 `steward_human_id`（格式嚴格為 `hid_<base32>`）。**

- 缺少 `steward_human_id` 將直接觸發 `ORG_STEWARD_REQUIRED`；
- 試圖以 `ifay_` 或 `cofay_` 充當主理人將直接觸發 `STEWARD_MUST_BE_HUMAN`。

這項設計確保了無論組織架構多麼龐大，生態中的每一個作用中 `coFay` 都始終有一名明確可定位的自然人主理人，對其章程合規性負直接監管責任。

## 4.3 正交單跳 `iFay` 管理委託與「禁止再委託」

在實務營運中，歸屬自然人或組織主理人不可能每分每秒親自簽署每一次日常維運與組態調度。為此，歸屬方或主理人可以將一個或多個受信任人類原型的 `iFay` 列入 `RoleCharter.managers`（例如 `["ifay_opsmanageralpha2345", "ifay_opsmanagerbravo2345"]`）。

正交管理委託嚴格遵循三道安全邊界：

1. **管理權絕不染指所有權**：對 `managers` 新增或移除任何 `iFay` 僅調整日常維運代表範圍，`owner` 保持紋風不動；管理代理無權發起所有權過戶，亦無權竄改 `RoleCharter` 的使命聲明與紅線禁令。
2. **受委託主體僅限 `iFay`**：日常管理動作必須依託具體人類原型監護下的個體化身完成，嚴禁將另一個 `coFay` 指派為當前 `coFay` 的管理代理（觸發 `MANAGER_TARGET_INVALID`），以防止形成跨公共角色的循環控制迴路。
3. **嚴格單跳，嚴禁二次轉委託（No Re-delegation）**：唯有 `owner.id` 或 `steward_human_id` 有權執行 `GRANT` / `REVOKE` 管理委託。若已獲授權的 `ifay_A` 試圖私自把管理權再轉授給 `ifay_B`，檢核器會立即拒絕並回傳 `MANAGER_REDELEGATION_FORBIDDEN`。這道單跳紀律徹底消除了權限鏈失控擴散的風險。

## 4.4 跨五大基礎設施的端對端權責協同鏈路

一個合規執行的 `coFay` 如何將上述權責模型貫穿至整個通訊協定堆疊？下方展示從身分創立到技能服務與聲譽記帳的完整五儲存庫協同拓樸：

```text
[FayID 1.0] 確立 hid_ / org_ / ifay_ / cofay_ 自主主權金鑰與單層歸屬關係
     │
     ▼
[coFay RoleCharter 1.0] 主理人簽發章程：鎖定角色原型、SSP/CAP 邊界與 managers[]
     │
     ├──▶ [Faying 1.1] (coFay Delegated Stewardship Profile)
     │      打通 Human Prime / Steward ──▶ iFay Manager ──▶ coFay 可驗證委託授權鏈
     │
     ├──▶ [SSP 1.0 & CAP 1.0]
     │      對外公開帶 cofay_ JWS 簽章的技能描述符；在 cap_bounds 內受控操作終端宿主(Host)
     │
     └──▶ [GMChain]
            將履職創造的社會貢獻記入 1:1 綁定的 MeritPocket（非貨幣美譽值 MeriToken）
```

具體而言：
- **與 `Faying 1.1` 的銜接**：`Faying 1.0` 聚焦於人類原型與其個人 `iFay` 的一對一配對且已發布凍結；生態透過向下相容的 **`Faying 1.1`（`coFay` Delegated Stewardship Profile）** 擴充規範（詳見 `Faying-Protocol`），在不破壞 1.0 的前提下承載「人類原型/組織主理人 → `iFay` 管理代理 → `coFay`」的可驗證委託憑證鏈與雙簽過戶授權語意。
- **與 `SSP 1.0` 的銜接**：呼叫端（通常為受人類原型 Mandate 約束的 `iFay`）在呼叫 `coFay` 技能時，`InvocationRequest.caller.id` 攜帶規範 `FayID`，而 `coFay` 會在描述符取得與呼叫執行兩側，對 `restricted` / `private` 技能強制執行雙向權限驗證（詳見 `Skill-Sharing-Protocol`）。
- **與 `CAP 1.0` 的銜接**：當 `coFay` 附身（Inhabit）並控制某台自助服務機台或業務應用宿主（Host）時，宿主驅動層會依據 `RoleCharter.allowed_capabilities.cap_bounds` 核驗授權描述符，攔截任何超出 `allowed_scopes` 或違反 `allow_irreversible_actions` 的指令（詳見 `Control-Authority-Protocol`）。

## 4.5 代表行為稽核留痕與離線可追溯性

為了確保在任何爭議處理或資安事後檢討中皆能還原真相，`coFay` 將**代表關係可追溯性**定義為不仰賴外部網路或特定區塊鏈連線狀態的本徵語意要求：

1. **絕不以自然人個人名義行事**：`coFay` 的一切對外聲明與回應均以「歸屬主體旗下的公共角色」名義作出；稽核紀錄一旦出現 `acting_as_natural_person: true`，立即判定違規（`NATURAL_PERSON_IMPERSONATION_FORBIDDEN`）。
2. **強制三元稽核錨點**：每一次對外呼叫、核准或狀態變更紀錄，都必須完整包含：
   - `cofay_id`：當前履職的公共角色識別碼；
   - `owner_id`：行為發生當下的法定單層歸屬主體識別碼；
   - `actor_signer_id`：實際簽署該次動作的金鑰主體（可為 `cofay_` 角色金鑰本身、歸屬方、主理人，或章程內作用中的某個 `ifay_` 管理代理；非授權簽章者將立即觸發 `AUDIT_ACTOR_UNAUTHORIZED`）。
3. **缺席可降級保證**：即使某個部署環境暫未接入 `GMChain` 主網或處於弱網隔離狀態，本機 `hash_chain` / `append_only` 稽核日誌依然完備保存上述三元組簽章證據，待網路恢復後再依需求錨定批次摘要。
